# 設問シートの生成指示（Step 1.5 用）

> 🔴 **これは `upstream-flow` スキルが持つ生成指示であり、配布される雛形ファイルではない。**
> `docs/framework-templates/` へは置かない（判定基準の正本は `docs/02_requirements/document-catalog.md` §4）。
>
> Step 1.5 では、この構成に沿って **対象リポジトリの `content/research/{ID}_prompt.md` を書き出す**。
> ファイルをコピーするのではなく、下記の構成を使ってその場で生成する。

## 生成する内容の構成

以下の見出し構成で `content/research/{ID}_prompt.md` を書き出す。`{}` の箇所はこの案件の内容で埋める。

---

### `# research-prompt: {プロダクト名}`

冒頭に 1 行、このシートの役割を書く: 「〇〇ができるツールを作りたい」という 1 行に対して、**要件（`FR-n` / `NFR-n`）の取捨と技術選定（`D-n`）を根拠付きで決めるための調査** を先に済ませるものである、と。

調査結果は `product-brief.md` の §7（リサーチ）から参照し、そこで得た事実を `FR-n` の採否理由・`D-n` の理由・`Q-n` の洗い出しに使う。ID クラスの扱い（リサーチ結果に ID を振らないことを含む）は `product-brief.md` §0 の記入ガイドに従う。

### `## 1. 調べる対象（1 行）`

ユーザーが持ち込んだ「作りたいもの」を、調査対象として 1 文に書き直す。

### `## 2. リサーチの深さ`

選んだ深さ（deep / light）と、その理由を 1 行。判定基準は SKILL.md Step 1.5 の表に従う。

### `## 3. 設問`

下の 5 類型から、この案件に効くものを **3〜5 本** 選んで具体化する。**全部やらない。**
**「その答えが要件と技術選定のどちらを動かすか」を書けない設問は削る**（調べる意味が無い）。

| 類型 | 何を調べるか | 答えが動かすもの |
|---|---|---|
| **既存ソリューション** | 同じ課題を解く既存プロダクト・OSS・SaaS はあるか。あるなら何が足りないか | `FR` の取捨 / そもそも作らない判断 |
| **技術的実現性** | 中核機能を実現する技術・API・ライブラリは実在するか。制約（レート制限・認証方式・データ形式）は何か | `FR` の実現可否 / `D` の選択肢 |
| **落とし穴・失敗事例** | 同種のプロダクトが躓く典型箇所は何か。運用が破綻するのはどこか | `NFR` / スコープアウト |
| **制約（法規制・利用規約）** | 扱うデータや呼び出す API に、法令・規約上の制限はあるか | スコープアウト / `D` の前提 |
| **コスト構造** | 運用コストは何で決まるか。利用が増えたとき何が効いてくるか | `D` の選択肢 / `NFR` |

各設問は「この案件で具体的に何を調べるか」まで落として書く（類型名のまま渡さない）。

### `## 4. 出力に求めること`

- 各設問への回答は **出典 URL 付き** で示す（出典の無い断定は採用しない）
- 「見つからなかった」も結論として明記する（沈黙で埋めない）
- 推測と事実を分けて書く
- 最後に **「この結果が要件・技術選定に与える影響」を 3〜5 行** でまとめる（これが `product-brief.md` §7 へ転記される）

---

## 生成後にやること

1. 深さに応じて実行する（実行手段は `SKILL.md` Step 1.5 の表に従う）
2. 結果（`content/research/{ID}_deep_research.md`）の「影響」を `product-brief.md` §7 へ転記する
3. 影響を踏まえて `FR-n` / `NFR-n` を確定する（調査前に書いた要件があれば見直す）
4. 技術選定（`D-n`）の理由欄に、根拠となった調査結果を参照として書く
5. 調査で新たに浮かんだ未確定事項を `Q-n` に追加する
