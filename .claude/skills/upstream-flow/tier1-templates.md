# Tier 1 カタログ 9 本の生成指示（Step 3.6 用）

> 🔴 **これは `upstream-flow` スキルが持つ生成指示であり、配布される雛形ファイルではない。**
> `docs/framework-templates/` へは置かない（判定基準の正本は `docs/02_requirements/document-catalog.md` §4。
> 同書 §3.3 `AC-4` 静的検査 S-1 は Tier 0 の `product-brief.md` 以外の雛形本体が同ディレクトリへ
> 先行配置されると落ちる）。
>
> Step 3.6 で `primary` が Yes と判定されたら、この構成に沿って **対象リポジトリの `docs/{ファイル名}.md`
> を書き出す**。既存ファイルをコピーするのではなく、下記の見出し構成 + 記入ガイドを使ってその場で生成
> する。各節の記入例（架空プロダクト「にゃんこ勤怠くん」）は `docs/framework-templates/{ファイル名}.example.md`
> を参照する。ID クラス（`FR-n` / `NFR-n` / `AC-n` / `D-n` / `Q-n`）を新規に振らない — それらの
> 正本は常に `product-brief.md`（`T0-1`）であり、Tier 1 の各書は参照するだけに留める
> （`document-catalog.md` §2 `T1-1` 行の原則）。

## T1-1: 初期要件（`docs/initial-requirements.md`）

対応する記入例: `initial-requirements.example.md`。

見出し構成:

```markdown
# 初期要件: {プロダクト名}

## 1. 受け取った要求（未構造化・原文に近い形）

## 2. 含まれる独立した要求（構造化前・ID を振らない）

## 3. 次工程への引き継ぎメモ
```

記入ガイド:

- §1: ユーザーから受け取った依頼文を、要約せずできるだけ原文に近い形で引用する
- §2: §1 に含まれる独立した要求を箇条書きに分解する。**ここでは `FR-n` 等の ID を振らない**
  （ID を振った時点で `product-brief.md`（`T0-1`）の責務になる・`document-catalog.md` §2 の原則）
- §3: 各要求を `product-brief.md` のどの節へどう構造化するか、または今回のスコープから外して
  `Q-n` や `3.1 やらないこと` へ回すかの方針を書く

### T1-4: ユーザーストーリーマップ（`docs/user-story-map.md`）

対応する記入例: `user-story-map.example.md`。

見出し構成:

```markdown
# ユーザーストーリーマップ: {プロダクト名}

## 1. バックボーン（ユーザー活動の大分類）

## 2. ストーリーマップ（活動 × 優先度）

## 3. リリーススライス
```

記入ガイド:

- §1: ユーザー活動を時系列・大分類で 1 行の流れとして書く（例: 「打刻する → 確認する → 申請する」）
- §2: 活動 × スプリント（`SP-n`）の表にし、各セルへ `product-brief.md` の `FR-n` を配置する。
  **要件内容・受け入れ条件の本文は再掲しない**（`FR-n` の ID 参照だけに留める・`document-catalog.md`
  の正本責務分離表）
- §3: `SP-n` ごとに含まれる `FR-n` を列挙する

### T1-5: ロードマップ（`docs/roadmap.md`）

対応する記入例: `roadmap.example.md`。

見出し構成:

## 1. マイルストーン一覧

- `SP-n` への分解・リリーススライスの詳細は T1-4 側の正本であることを末尾に 1 行明記する

## T1-6: アーキテクチャ / ドメインモデル定義（`docs/architecture.md`）

対応する記入例: `architecture.example.md`。トリガー: `D-n` にアーキテクチャ様式（レイヤード・
ヘキサゴナル等）または複数モジュールの責務分割が記録されたとき。

見出し構成:

```markdown
# アーキテクチャ / ドメインモデル定義: {プロダクト名}

## 1. 層構造

## 2. 依存規則

## 3. モジュール分割（責務）

## 4. ユビキタス言語（最小限）
```

記入ガイド:

- §1: 層構成を Mermaid（`graph TD`）で描く。co-location（本書と同一ファイル）なので鮮度ゲートは不要
  （`document-catalog.md` §5.2）
- §2: 層ごとに依存してよい先を表にする。`product-brief.md` §5.0 で実装モデル（クリーンアーキテクチャ・
  DDD・TDD）を外している場合は、外した範囲を踏まえて書く（`D-4` 相当の opt-out を参照）
- §3: モジュールと、それぞれが担う `FR-n` を列挙する
- §4: 用語の表記ゆれを防ぐ最小限の対応表（「別名を使わない」の形で書く）

## T1-7: デザイン定義・ビジュアル（`docs/design-definition.md`）

対応する記入例: `design-definition.example.md`。トリガー: `D-n` にフロントエンド技術の選定が記録され、
かつトンマナ・配色・ブランドへの言及があるとき。

🔴 **T1-8 との境界**: 本書は「どう見えるか」の **値** だけを持つ。「どう動くか・どう辿るか」の設計は
混ぜず T1-8 側に置く（`document-catalog.md` §2 の注記）。T1-7 は T1-8 の真部分集合トリガーのため、
同時成立時は本書が優先提示される（`document-catalog.md` §3.2 item 3）。

見出し構成:

```markdown
# デザイン定義・ビジュアル: {プロダクト名}

## 1. デザイントークン

## 2. トンマナ

## 3. ブランド指針
```

記入ガイド:

- §1: プライマリカラー・アクセントカラー・ベースフォント・スペーシング単位を表にする
- §2: `D-n` の理由欄に書かれたトンマナの要望を反映する（新しい方向性を作らない）
- §3: `M-1` 段階でブランディングが範囲外なら、その旨を明記して節を薄く保つ（先回りで作り込まない）
