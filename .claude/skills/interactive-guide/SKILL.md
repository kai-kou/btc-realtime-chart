# interactive-guide — ユーザーと交互に進める対話型ガイド

> **位置付け**: Claude の自律実行が **原理的に届かない工程** だけをユーザーに委ね、その工程を最小の摩擦で完了させるためのスキル。
> CP-6（ユーザー介入最小化）と衝突しない理由は Step 0 を参照。A-1〜A-5 が「Claude が実行できるが承認が要る行為」であるのに対し、本スキルは **「Claude に実行手段がない行為」** を扱う別軸。A-6（アカウント設定・課金設定）は両方の性質を持つため、承認だけで済むなら通常の確認フロー、ユーザーが画面を操作する必要があるなら本スキルに乗せる。

---

## Step 0: 起動条件（2 ゲート・省略禁止）

**適用単位は「工程」であり「依頼全体」ではない。** 1 依頼の中に自律実行できる工程と本スキルが必要な工程が混在するのが通常形で、自律実行できる工程はそのまま Claude が実行し、下の 2 ゲートを通過した工程だけを本スキルのループに乗せる。

- [ ] **ゲート 1（代替経路と実行可能性の確認）**: 対象操作に CLI / 公式 API / MCP が存在しないかを調べる。存在すれば実際に 1 回呼び出す（**呼び出してよいのは `--help` / list / get / dry-run 等の非破壊的な確認だけ**。送信・作成・課金・権限付与など副作用のある操作は呼ばず、経路が存在する事実と認証が通ることの確認に留める）。**存在するが呼び出せない場合は「なぜ自動実行できないか」を 1 行で記録する**（例: 「Slack の `apps.manifest.create` は存在するが、config token は管理画面への対話ログインでしか発行されない＝起点が人手」）。記録なしに「無理」と判定しない（L-077 と同じ鉄則）。
- [ ] **ゲート 2（操作主体の確認）**: その工程が「ユーザー本人の権限・身体・所有物でしか実行できない」ことを 1 文で説明できる。

**適用対象の例**: ユーザー本人の PC / スマートフォンでの GUI 操作（インストーラ実行・OS 設定）/ API・CLI・MCP を一切提供しないサードパーティ管理画面の設定 / 2FA コード入力・CAPTCHA・生体認証などユーザー本人の身体的操作が必須の工程（A-6 の課金・アカウント設定もここに含む）。

**起動してはならない例**: MCP・公式 CLI・REST API で代替できる操作 / 単に試していないだけでクラウド実行できる操作（`docs/rules/user-confirmation-minimization.md` §4「ローカル実行が必要アンチパターン」に該当）。

> **ゲートの実行はサイレント**（L-111）。「ゲート 1 を確認中」等の実況は出さない。ゲートの **結果だけ** を、ゲート不通過なら通常の自律実行の完了報告に、通過なら Step 1 サマリーの「事前に必要なもの」欄に 1 行で織り込む（例: 「{サービス名} には公式 API がなく、画面操作が必要です」）。着手直後の `output-verbosity-rules.md` §1.1 プラン提示を先に 1 回出しておけば、ゲート実行中の沈黙はユーザーに違和感を与えない。

## Step 1: 全体像サマリーを提示する（開始前に 1 回）

個別手順（URL・入力値）はここに書かない。サマリーは地図、各工程の案内は曲がり角ごとの指示。

**このサマリーが `output-verbosity-rules.md` §1.1 の着手時プラン提示を兼ねる。** ゲート通過後に §1.1 のプラン提示と本サマリーを二重に出さない（同じ「これから何をするか」を 2 連続で告知することになる）。

```markdown
## 🧭 これから一緒に進める作業: {タイトル}

- **工程数**: 全 {N} 工程（目安 {M} 分）
- **事前に必要なもの**: {アカウント / 権限 / ログイン済みであること 等。無ければ「特になし」}
- **完了すると得られるもの**: {1 文。例: 「Bot Token が発行され、リポジトリの Secrets に登録された状態」}
- **進め方**: 1 工程ずつ案内します。完了確認が取れたら次に進みます。画面が違う・詰まったときは、そのまま伝えてください。

準備ができたら「開始」と送ってください。
```

工程数と所要時間を先に示さないと、ユーザーは「あと何往復か」が読めず離脱する。この 4 要素は過不足なしで固定する。

## Step 2: 1 工程ループ（全工程を消化するまで繰り返す）

### 2-1. 案内する直前にリサーチする（サイレント）

- その工程で提示する **URL・画面のラベル・メニュー階層** を、提示直前に一次情報（公式ドキュメント・公式ヘルプ）で確認する。ツールは `WebFetch`（公式ドキュメント直引き）> `context7`（ライブラリ・API 仕様）> `WebSearch`（公式が曖昧・404 のときの代替探索）の順で選ぶ。
- 検証するのは **このウォークスルー内で初めて提示する URL** のみ。同一画面内で工程が続く場合の再検証はしない（帯域の無駄）。
- リサーチ過程は実況しない。結果を案内文に統合して 1 回で出す。

### 2-2. 1 工程分だけ案内する

1 工程 = 1 意思決定 または 1 入力フォーム相当。「ログインして設定画面を開いて API キーを発行する」は 2〜3 工程に割る。

```markdown
## 工程 {n}/{N}: {工程名}

1. [{ページ名}]({URL}) を開いてください
2. {クリックする箇所を 1 動作}
3. {入力する値がある場合は 2-3 のコピペ書式で}

**完了したら**: {口頭 or キャプチャの指定}で教えてください。
```

**入れないもの**: 次工程以降の先出し / 長い背景説明（必要なら 1 行に圧縮）/ 既に案内済みの内容の再掲。

### 2-3. 入力項目は 1 項目 1 コードブロックで渡す

複数の値を 1 ブロックにまとめない（不要な行までコピーされる事故を防ぐ）。

~~~markdown
**Bot Token Scope** に入力:
```
chat:write
```

**Redirect URL** に入力:
```
https://example.com/callback
```
~~~

値が既に判明している **非秘密の値**（リポジトリ名・メールアドレス・エンドポイント URL 等）は **実値を埋めて渡す**。`{YOUR_VALUE}` のようなプレースホルダのまま渡さない（ユーザーの二度手間になる）。

> 🔴 **API キー・トークン・パスワード等の秘密情報は実値を書かない。** チャット履歴・Issue コメントに平文で永続化される。「先ほど発行された値をそのまま貼り付けてください」と **参照で案内し、Claude 側でも値を保持・再掲しない**。

### 2-4. 完了確認を取ってから次へ進む

**キャプチャを求めるかどうかの判定原則（これ 1 つ）**:

> 次のどちらかに当てはまれば **キャプチャ必須**、どちらでもなければ **口頭で「できた」の一言で OK**。
> 1. **その工程を誤っても、後続の案内やキャプチャで自然に発覚しない**（誤りが静かに埋没し、気づいた時の手戻りが大きい）
> 2. **直前のリサーチが、その画面の表示バリエーション（選択肢の数・条件分岐）まで確認できていない**（最新情報を持っていても実画面と食い違いうる。この軸を落とすと UI 差異の検知そのものが機能しない）

**判定に迷ったらキャプチャを求める側に倒す**（画像 1 枚のコストより、数工程後に発覚する手戻りコストの方が大きい）。

典型例: 初訪問の画面（比較対象がなく誤りが埋没する）/ 選択によって以降の手順が変わる分岐画面 / 取り消しが困難な操作の直前（課金・権限付与）。

> 🔴 **秘密情報が画面に表示される工程はキャプチャを求めない**（発行直後の API キー画面など）。画像はチャット履歴に平文で残る。この場合は「発行できたら『できた』と一言ください（値は送らないでください）」と口頭確認に切り替える。

```markdown
**完了したら**: 「できた」と一言で OK です。次に進みます。
```
```markdown
**完了したら**: この画面のキャプチャを送ってください（初めて開く画面のため、表示項目を確認します）。
```

**キャプチャを求めるときは理由を 1 句添える。** 理由なしの要求は「なぜ今回だけ？」という摩擦を生む。キャプチャが難しい場合はテキストの説明でも進めてよい。

## リカバリ（詰まった / 画面が違うと言われたとき）

```
1. キャプチャ（あれば）または文面から現在地を特定する
2. 最新の UI 情報を再リサーチし、UI 変更由来か操作ミス由来かを切り分ける
3. 現在地から「次の一手」だけを再提示する（工程全体をやり直させない）
4. 同じ工程で 2 回詰まったら、別経路（別メニュー・CLI 代替）を提示する
5. ユーザーの応答が途切れたら、進捗を記録して対象 Issue に status:waiting-user を付けて中断する
   （次セッションが Issue から現在地を復元して再開できる）
```

**キャプチャと手順が食い違ったら、キャプチャを正とする。** 同じターンのうちに一次情報を引き直し、差分を明示して（例: 「『設定』タブは『環境設定』に名称変更されています」）修正案を返す。矛盾を曖昧なまま次工程へ進めない。

## UI 手順の確度管理（L-113 の姉妹制約・省略禁止）

UI のラベル・配置は頻繁に変わり、訓練データの記憶は最新でない可能性が高い。**未確認の手順を確認済みとして提示するのは、L-113（ツール結果を自分で書いて事実と思い込む）と同型の捏造。**

- **記憶だけを根拠に「◯◯ ボタンをクリックしてください」と断定しない。** 案内を出す前に URL を `WebFetch` で実際に取得し、**返り値の内容そのもの** を根拠に手順を書く（どの URL を検証するかの範囲は Step 2-1 に従う）。
- **取得できなかった URL（404・エラー・無関係な内容）は提示しない。** `WebSearch` で代替 URL を探し直す。URL は必ず Markdown リンク記法で書く（bare URL は末尾の約物を巻き込んで 404 になる・L-112）。
- **どちらも満たせない場合は断定形を避ける**: 「{意味的に相当する項目} という名称のボタンを探してください。見当たらなければキャプチャを送ってください」とヘッジする。

## 進捗の記録（状態管理は作り込まない）

専用の状態ファイル・進捗 JSON は作らない（クラウドではセッション間でファイルシステムが共有されず、圧縮後のクリーンアップでも壊れる）。記録先は **対象 Issue のコメント 1 行** に一本化する（`session-compression-rules.md`「セッションをまたぐ作業状態は Issue / PR コメントに明示コミットする」の適用）。

打つタイミングは **着手時（Issue 作成 + Done Criteria）/ キャプチャ必須と判定した工程の完了時 / 全工程完了時** のみ。口頭確認だけで進む工程では打たない。

```
進捗: 工程 3/6 完了（API キー発行済み）
```

**進捗行に秘密情報（トークン・キー・パスワード）を書かない。** 工程名だけを書く（「API キー発行済み」は可、値は不可）。

`user-instruction-issue-rules.md` の基準で Issue 化不要と判定した軽微な作業（数分・単一工程）では対象 Issue が存在しないため、**進捗記録そのものを省略する**。

中断からの復帰は「Issue のコメント履歴を読んで現在地を復元する」で足りる。

## 出力方針（L-111 との関係）

- **工程ごとの案内は L-111（内部作業サイレント）の対象外。** L-111 が禁じるのは Claude 自身の検証・実装ループの実況（ユーザーには不要な作業ログ）であり、本スキルの逐次案内は **ユーザーが次に行う操作そのもの＝成果物** で、省略するとタスクが遂行不能になる。
- **逆に、工程の合間で Claude が行う調査・キャプチャ解析はサイレントに実行する**（判定基準と実行手順は Step 2-1 を参照）。
- 着手時のプラン提示は Step 1 の全体像サマリーが兼ねる（`output-verbosity-rules.md` §1.1 の書式と二重に出さない）。

## 完了報告

全工程が完了しユーザーの最終確認が取れた時点で、`docs/rules/completion-report-rules.md` の構造（ご依頼の再掲 → できるようになったこと）で締める。途中の工程案内は完了報告ではないため、同フォーマットを毎回付けない。

## 禁止パターン

- Step 0 のゲートを飛ばして起動する（判定基準は Step 0 が正本。自律実行できる作業をユーザーに丸投げする誤発火は本スキル最大の事故）
- 秘密情報（トークン・キー・パスワード）を案内文・進捗コメントに実値で書く / 秘密情報が表示される画面のキャプチャを求める
- 初手で全工程の手順を一覧で並べる（要件は「1 工程ずつ」）
- 記憶だけで UI 手順・URL を断定する（L-113 同型の捏造）
- 複数の入力値を 1 コードブロックにまとめる / プレースホルダのまま渡す
- 全工程で一律にキャプチャを要求する（摩擦とターン数の浪費。判定原則に従う）
- 専用の進捗ファイル・状態管理スクリプトを作る（YAGNI・クラウドで壊れる）
