## 0. ID 体系の使い方（記法ガイド）

このドキュメントでは次の意味論クラスの ID だけを使う。**プロダクトごとに具体的なプレフィックスやセクション構成を作り込む必要はない**。使うのは以下のクラスだけで、下記以外の新しい種類を自作しない:

| クラス | 意味 | 使う場所 |
|---|---|---|
| `FR-n` | 機能要件（Functional Requirement） | §3 やりたいこと |
| `NFR-n` | 非機能要件（Non-Functional Requirement） | §3 やりたいこと（非機能） |
| `AC-n` | 受け入れ基準（Acceptance Criteria） | §4 完了の定義 |
| `D-n` | 決定（技術選定・仕様上の決定） | §5.1 決定ログ |
| `Q-n` | 未決事項（まだ決まっていないこと） | §6 未決事項 |

🔴 **必要な ID だけを使う。全部埋めようとしない。** 小さなプロダクトなら `FR-1`〜`FR-3` と `AC-1`〜`AC-2` だけで十分なことが多い。ID 番号は欠番があってもよい（`FR-1` の次が `FR-3` でも構わない）。

## 1. 課題（何を解くのか）

BTC を短期売買する人は、価格の変動を秒単位で追いながら「今は買い時か・売り時か」を判断したい。
取引所の画面は注文機能が主役で重く、テクニカル指標の設定も毎回手間がかかる。
ブラウザを開くだけで最新のローソク足とボリンジャーバンド、売買シグナルが常に表示される、
トレーディングの参考専用の軽い画面が欲しい。

## 2. 想定利用者

BTC を短期〜デイトレードで売買する個人（まずは依頼者本人）。PC ブラウザで常時表示し、スマートフォンでも確認する。

## 3. やりたいこと（スコープイン）

- `FR-1`: BTC の価格をローソク足チャートで表示し、WebSocket で受信した約定ごとに形成中の足を更新する
- `FR-2`: ボリンジャーバンド（20 期間・±2σ）と中心線をチャートに重ねて描画する
- `FR-3`: ボリンジャーバンドと RSI(14) を組み合わせた買い時・売り時のシグナルを、確定足ごとにチャート上へマーカーで描画する
- `FR-4`: 時間足を切り替えられる（1 分・5 分・15 分・1 時間・4 時間・1 日）
- `FR-5`: 最新の足が常に見えるようにする。新しい足で右端へ自動追従し、過去へスクロールしたときは「最新へ」ボタンで戻れる
- `FR-6`: 接続状態と最終受信からの経過時間を表示し、切断・無通信・タブ復帰・オンライン復帰のときは自動で再接続し、欠けた足を取り直す
- `FR-7`: 現在値・前足比・%B・RSI・現在の状態（バンド内・下限付近など）をパネルに表示する
- `NFR-1`: 約定受信から画面反映までの遅延を 1 秒未満にする（中継サーバーを挟まず、ブラウザから取引所へ直接接続する）
- `NFR-2`: インフラは Cloudflare を使い、固定費 0 円（無料枠）で運用できる
- `NFR-3`: 主データ源が使えない地域・障害時は、自動で別のデータ源へ切り替えて表示を続ける

## 3.1 やらないこと（スコープアウト）

- 注文・口座連携（参考表示専用。API キーを扱わない）
- 売買シグナルのバックテスト・収益シミュレーション
- 円建て表示（`Q-1`）
- 利用者ごとの設定保存・ログイン

## 4. 完了の定義（受け入れ基準）

- `AC-1`: Cloudflare 上の公開 URL をブラウザで開くと、直近の BTC ローソク足・ボリンジャーバンド・出来高・RSI が表示される
- `AC-2`: 表示中に価格が秒単位で更新され、接続状態が「LIVE」になる（ブラウザ自動テストで確認する）
- `AC-3`: 指標とシグナル判定のユニットテストがすべて通る
- `AC-4`: 過去足でシグナル条件を満たした位置に BUY / SELL マーカーが描画される
- `AC-5`: WebSocket を強制切断すると、自動で再接続して LIVE に戻る

| ID | 決定事項 | 理由 | タグ | ADR 化（3 条件 AND を満たすか） |
|---|---|---|---|---|
| `D-1` | ホスティングは Cloudflare Workers の静的アセット配信（Worker スクリプトなし・`_headers` で CSP 等のセキュリティヘッダーを付与） | ユーザー指定（Cloudflare）。処理はすべてブラウザ側で完結するためサーバー処理が不要で、静的アセット配信なら無料・リクエスト数上限なしで運用できる（`NFR-2`） | deploy | いいえ |
| `D-2` | 主データ源は Binance の市場データ専用エンドポイント（REST `data-api.binance.vision` で過去 1000 本・WS `data-stream.binance.vision` で aggTrade + kline を購読）。通貨ペアは BTC/USDT | 取引量が最も多く、約定ごとの配信で最もリアルタイム性が高い。通常のエンドポイントは地域制限（451）があるが、市場データ専用エンドポイントは実測で接続できた（§7） |  | いいえ |
| `D-3` | Coinbase Exchange（BTC-USD・matches チャネル）を自動フェイルオーバー先にする。ローソク足は約定から組み立て、4 時間足は 1 時間足から合成する | 主データ源が地域制限・障害で使えないときも表示を続けるため（`NFR-3`）。Coinbase の candles API には 4 時間足が無い（§7） |  | いいえ |
| `D-4` | ブラウザから取引所へ WebSocket で直接接続し、Cloudflare 側で中継しない | 中継を挟むと遅延と運用コスト（Durable Objects 等）が増える。利用者が増えて取引所の接続上限が問題になったら、Durable Objects による集約配信へ切り替える | architecture | いいえ（後から中継を足せるため不可逆ではない） |
| `D-5` | チャートは TradingView Lightweight Charts v5（Apache-2.0）をバンドルして配信する（CDN に依存しない） | ローソク足・複数ペイン・マーカーに標準対応し、軽量（約 45KB gzip）。CDN 障害の影響を受けないよう自前で配信する | frontend | いいえ |
| `D-6` | 売買シグナルは「前の足がバンド外で引け、今の足がバンド内へ戻った」かつ「RSI が 35 以下（買い）/ 65 以上（売り）」の確定足だけで判定し、同じ向きのシグナルは 5 本空ける | バンド外へのはみ出しだけで判定すると強いトレンドで連発して使い物にならないため、平均回帰の反転と RSI の過熱感を条件にした。確定足だけで判定するので、表示後にシグナルが消えたり動いたりしない |  | いいえ |
| `D-7` | フロントエンドはフレームワークを使わず、素の JavaScript（ES Modules）を esbuild でバンドルする | 画面は 1 枚だけで状態も少なく、フレームワークを入れる利点が小さい。依存を最小にして配信サイズを抑える | frontend | いいえ |

### 要件・技術選定に与えた影響

<!-- 調査結果の「影響」まとめを 3〜5 行で転記する。どの FR-n / D-n / Q-n を動かしたかが分かる形で書く。 -->

- bitFlyer（円建て）は公式の過去足 API が無いため見送り、`Q-1` として残した
