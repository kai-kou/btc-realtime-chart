## 1. 課題（何を解くのか）

架空の小規模合同会社「ねこ雑貨合同会社」（従業員 8 名・架空の組織）では、勤怠を紙の出勤簿と口頭申告で管理しており、月末の集計に総務担当が毎回半日を費やしている。また有給残日数を従業員自身が把握できず、総務への問い合わせが月に十数件発生している。

## 2. 想定利用者

- 従業員 8 名（Slack 相当の社内チャットは使っているが勤怠管理ツールは未導入という想定）
- 総務担当 1 名（月末集計・有給管理を行う）

## 3. やりたいこと（スコープイン）

- `FR-1`: 従業員が Web 画面から出勤・退勤を打刻できる
- `FR-2`: 従業員が自分の有給残日数をいつでも確認できる
- `FR-3`: 総務担当が月次の勤怠一覧を CSV でダウンロードできる
- `NFR-1`: 打刻画面はスマートフォンのブラウザ（架空の想定端末）から問題なく操作できる
- `NFR-2`: 打刻データの保存先は `example.com` 配下の架空のテスト環境を用いる（実在のクラウド事業者名は記載しない）

## 3.1 やらないこと（スコープアウト）

- 給与計算との連携（今回は勤怠記録と集計まで。給与計算は別プロダクトの範囲とする）
- 打刻位置情報による不正打刻検知（要望はあるが優先度は低いため今回は対象外）

## 4. 完了の定義（受け入れ基準）

- `AC-1`: 従業員アカウントでログインし、出勤・退勤の打刻ボタンを押すと、打刻時刻が記録され画面に反映される
- `AC-2`: 従業員が「有給残日数」画面を開くと、現在の残日数が表示される
- `AC-3`: 総務担当が「月次エクスポート」ボタンを押すと、対象月の全従業員分の打刻記録が CSV としてダウンロードできる

### 要件・技術選定に与えた影響

既製の勤怠管理 SaaS が 8 名規模でも一定の月額を要し、かつ有給残日数の表示が上位プランに限られる例が複数見つかったため、`FR-2`（従業員自身が有給残日数を確認できる）を中核要件として残す判断をした。労働時間の記録は一定期間の保存が求められるとする情報が複数の一次情報で一致したため、打刻データを揮発的なストレージに置かない前提を `D-1` の理由に加えた。一方で「位置情報による不正打刻検知」は同種プロダクトで運用が形骸化しやすいという指摘が複数あり、`3.1 やらないこと` に残す根拠になった。CSV の列構成については決め手となる情報が見つからず、`Q-2` として未決のまま残している。
