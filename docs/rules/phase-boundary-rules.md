# フェーズ境界ルール（Phase Boundary Rules・Hot 層サマリー）

> **SSOT**: 「要件定義フェーズと実装フェーズで確認の許容度がなぜ変わるか」の唯一の正本。
> 背景・実測根拠・逆流検知ゲート・既知の限界・参照表は `phase-boundary-rules-detail.md`（Warm 層）。
> `CLAUDE.md`「🔴 フェーズ変数」節は本ファイルのさらに要約。

## なぜ必要か（1 行）

C-1〜C-4（要件定義・技術選定）は対話で決める工程で、`CP-6`/`SD-3`（自律運転）と字面上ぶつかる。確認の許容度をフェーズ変数で切り替えて両立させる（背景全文は detail 版 §1）。

## 判定フロー（機械的・新しい状態を発明しない）

判定材料は「いま作業対象にしている Issue に `sp:N` ラベルがあり、`status:in-progress` で着手中か」の 1 点だけ。

| フェーズ | 判定条件 | 確認の許容度 |
|---|---|---|
| **要件定義**（grilling 型） | `sp:N` 無し、または `sp:N` 付きだが未着手（`status:in-progress` 無し） | C-1〜C-4 についてユーザーに **多く聞いてよい**。決定の主体はユーザー |
| **実装**（`CP-6`/`SD-3` 型） | `sp:N` 付きで **`status:in-progress`** 着手中 | 通常運転どおり **A-1〜A-6 と仕様解釈の分岐以外は聞かない** |

Issue ごとに判定する（全体の単一モードではない）。判定はコマンド 1 つで得られる（クラウドでは `--labels` に MCP 取得済みラベルを渡す）:

```bash
python3 tools/check_phase.py --labels "sp:3,status:in-progress"   # → 実装フェーズ / 要件定義フェーズ
```

## 実装フェーズの発火ライン（`SD-3` 相当・2 点のみ）

| 判定 | 行動 |
|---|---|
| ✅ 仕様解釈が **2 通り以上あり選択で成果物が変わる** | `AskUserQuestion`（選択肢は最大 2 つ・各 1 行の判断材料・推奨案に `（推奨）`） |
| ❌ 実装手段・ライブラリ選定・命名・ファイル分割・テストの書き方 | 自律実行し、仮定を Issue コメントか最初のコミットメッセージに 1 行記録 |

> ⚠️ `sprint-development-rules.md`（`SD-3` の正本）は本リポジトリに未移植。移植されるまで上表を発火ラインの正とする（経緯は detail 版 §1）。

## 🔴 A-1〜A-6 の定義は変更しない（不変の境界）

要件定義フェーズが「多く聞いてよい」のは C-1〜C-4 の決定事項だけで、`user-confirmation-minimization.md` §1 の既約境界外リスト（A-1〜A-6）を拡張・格上げする権限ではない。`tools/triage_notification.py` の `mention = (action_class == "A")` は A の希少性が前提の設計で、A を日常化すると通知の信号価値が壊れる（実測根拠は detail 版 §2）。C-5/C-6 のユーザー操作が要る場面はフェーズに関わらず引き続き **A-6**。

## 要件定義フェーズの質問の作法（要点）

- **1 ラウンドにつき frontier をまとめて聞く**。曖昧点 1 つで手を止めない。**frontier** は「前提が既に確定していて、いま決められる決定」の集合を指し、**終了条件は frontier が空になること**（黙って仮定したまま残っている決定がゼロになること）。🔴 **ラウンド数の上限ではない**（「ヒアリングは 1 回だけ」と読まない）。実装は `.claude/skills/upstream-flow/SKILL.md` Step 1・借用元の帰属は `NOTICE`（`D-33`）
- 各問いに推奨案を添える（`user-confirmation-minimization.md` §3 item 8 の書式要件に従う）
- **決定はユーザーのもの**。合意（回答）を得るまで後続作業に着手しない
- **質問の前に必ずコミット & push する**（`session-safety-rules.md`「ユーザー確認前の基本手順」。Stop フックの自動コミット等と噛み合わないため。詳細は detail 版 §5）
