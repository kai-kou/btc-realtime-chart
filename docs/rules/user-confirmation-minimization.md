# ユーザー確認最小化フレームワーク（既約境界外リスト SSOT）

> **このファイルは CP-6（ユーザー介入最小化）の実装中核であり、「ユーザー確認が必要なアクション（既約境界外リスト）」の唯一の正本（SSOT）である。**
> 派生先（`core-principles.md` / `autonomous-operation-policy.md` 等）はサマリーを持ってよいが、必ず本ファイルへの参照を併記する（参照なしの独立した重複定義は禁止）。
> `.claude/rules/` に symlink され、全セッションで自動読み込みされる。

---

## 0. 大原則: 「確認したくなったら、まず分類する」

ユーザーに「〜してよいですか？」「〜できないので確認お願いします」と言いそうになった **瞬間** が発動トリガー。

```
確認したくなる事象を検知
  ↓
それは「障害（エラー・想定外挙動）」か「判断（どう進めるべきかの選択）」か？
  ├─ 障害 → problem-investigation-protocol.md の5ステップを完全実施
  │         （自己解決できたら確認不要。尽くした上で残った真の課題のみ本フレームワークへ）
  └─ 判断 → §2 の A/B/C/D 分類に必ず落とす
        ├─ A（既約境界外）→ §1 のリストに完全一致するか確認 → 一致時のみユーザー確認可
        ├─ B（ツール改修で自律化可能）→ §4: まずクラウド実行を試行。失敗証跡を残して実装 Issue へ
        ├─ C（ルール整備で自律化可能）→ §5 に従い実行
        └─ D（外部要因）→ §6 のフォールバック/監視で影響を自律的に最小化
```

**「A に一致しない確認は、原則として CP-6 違反である」** ことを常に自問する。

> **仕様確定フェーズ（Think Before Coding）**: タスク受領直後の **仕様の曖昧さ** は上記フローの前段階。
> 最も単純な合理的解釈で推進できるなら **仮定を 1 行記録して自律実行** する（A-1〜A-6 相当の不可逆リスクがない限り質問不要）。4 分岐は §3 item 0。

## 1. 既約境界外リスト（Irreducible Boundary）

以下の **これだけ** が、真にユーザーの最終判断・操作を必要とする。安易な追加は禁止（追加時は本ファイルの更新 + 理由の明記が必須）。

| # | アクション | なぜ既約か | 既存の自律カバレッジ（通常はここで完結） |
|---|-----------|-----------|----------------------------------|
| **A-1** | `main` ブランチへの直接 push | 保護ブランチ。誤マージ時の影響が不可逆 | 全変更は作業ブランチ → PR → セルフレビュー → **自動マージ** で main 反映 |
| **A-2** | 外部公開（取り消し困難な公開）の **即時手動実行**（プロジェクトで具体化） | 収益・ブランドに直結し取り消し困難 | 通常公開はプロジェクト定義の自動スケジュールで完結。即時手動公開は緊急時のみ |
| **A-3** | 品質ゲート **致命的 NG** 時のパイプライン続行 | 誤り・事故の公開リスク | ① 軽微な指摘（閾値内）→ **自動マージ** / ② 閾値超過 → **自動 STOP + 通知 + `status:waiting-user`** / ③ 致命的 NG（虚偽断定・出典皆無等）→ **本行のユーザー確認** |
| **A-4** | サーキットブレーカー発動（修正サイクル 2 回超）後の続行判断 | 無限ループ・予算浪費の防止 | 2 サイクルまでは自律修正。発動後は §3 のテンプレートで報告 |
| **A-5** | 新規マイルストーンの追加 | プロジェクト計画の骨格に影響 | 既存マイルストーンへの Issue 割当は自律実行可 |
| **A-6** | プラットフォームの **アカウント設定・課金設定** の変更（GitHub Billing / API の課金・クレジット購入 / コンソールの API 有効化 / OAuth トークン再発行） | ユーザー個人アカウントの権限が物理的に必要 | §6 の監視・フォールバックで「枯渇前に予告」「枯渇後も代替手段で継続」。設定変更そのものだけがユーザー作業 |

> **重要**: A-6 であっても、「設定変更が必要」と判定する前に §4・§6 のクラウド実行試行・代替手段検証を必ず尽くす。「環境変数がない」「API 失敗」を理由にした即エスカレーションは L-077 違反。

**誤分類の常習パターン**（A に見えるが違う）: 「外部公開・制作処理はローカル実行が必要」→ **B**（認証情報はセッション env から取得可・クラウドで実行実績あり）/ 「環境変数がないので設定してほしい」→ **C/A-6**（まず問題調査プロトコルの A 型チェックリスト。真に未供給なら A-6 として設定名・手順付きで依頼）/ 「レポートを確認してほしい」「リサーチ依頼」→ **C**（担当スキルが自律実行）。プロジェクト例の詳細表は `user-confirmation-minimization-detail.md`。

## 2. 確認候補の A/B/C/D 分類フレームワーク

| 分類 | 定義 | 既定の行動 |
|------|------|-----------|
| **A: 既約境界外** | §1 のリストに **完全一致** する | コミット & push 後、§3 テンプレートでユーザー確認 |
| **B: ツール改修で自律化可能** | 実装すればクラウドで自律実行できるが、現状ツールが未対応 | §4: クラウド実行を試行 → 失敗証跡を残す → 実装 Issue へ（自動 escalation 禁止） |
| **C: ルール整備で自律化可能** | 判断基準を明文化すれば人間不要 | §5 に従い即実行 |
| **D: 外部要因** | 課金上限・アカウント BAN・プラットフォーム制約 | §6: 監視で予告 + フォールバックで継続。設定変更（A-6）のみユーザーへ |

**判定に迷ったら B または C と仮定する**（A への安易な分類は CP-6 違反のリスクが高い）。

> **PR 作成・マージは A に含まれない＝自律対象**（恒久委任）。SSOT は `CLAUDE.md`「PR 作成の完全自律化」。

## 3. エスカレーション前 必須チェックリスト

ユーザー確認に回す前に、以下を **全て** 満たしていること。1 つでも未達なら確認に回してはならない。

```
[ ] 0. （タスク受領時のみ）仕様の曖昧さは 4 分岐で処理する:
       (a) 最も単純な合理的解釈で解決できる → 仮定を 1 行記録して推進（質問不要）
       (b) 既存ルールに判断基準がある       → ルールに従い自律実行（質問不要）
       (c) 影響が不可逆かつ推奨案を作れる   → item 7・8 を満たしてユーザーへ確認
       (d) 推奨案すら作れない underdetermined → 理由を明記して情報提供依頼（最終手段・稀）
[ ] 1. 事象を §2 の A/B/C/D に分類した
[ ] 2. 分類 A の場合、§1 のどの行（A-1〜A-6）に一致するか明示できる
[ ] 3. 障害起因なら problem-investigation-protocol.md の5ステップを完全実施した
[ ] 4. B の場合、クラウド実行を実際に試行し、失敗ログ（コマンド・エラー全文）を残した
[ ] 5. 「ローカル実行が必要」と書く前に、detail 版 §4 のクラウド実行可能リソース表を確認した
[ ] 6. 既存ナレッジ（lessons / Issue / SKILL.md）を grep で検索した
[ ] 7. 未コミット変更を全てコミット & push した（session-safety-rules.md）
[ ] 8. 確認内容に「推奨案」を必ず添えている（丸投げ質問は禁止）
```

**item 8 の書式要件**（ユーザーが数秒で選べる形にする）: **選択肢は最大 2 つ**（3 つ以上に割るのは、判断材料を渡す代わりに判断そのものを丸投げしている）・**各選択肢に 1 行の判断材料**（何が変わるか / 何を失うか）・**自分ならどちらを選ぶかを明示**（推奨は「あってもいい情報」ではなく必須）。`AskUserQuestion` を使う場合も同じで、推奨案を先頭に置き `（推奨）` を付ける。

報告フォーマットは `session-safety-rules.md` の「Issue コメント記録テンプレート」に従う。

## 4. 「ローカル実行が必要」アンチパターンの撲滅ルール

waiting-user Issue の最大カテゴリは「ローカル実行が必要」だが、その多くは **desync**（インフラはクラウドで動くのに、ドキュメント/スキルが「ローカル必須」と古いまま）である。

**鉄則: 「ローカル必須」と宣言する前に、クラウド実行を実際に試す。**

```
1. detail 版 §4 のリソース表で、該当リソースがクラウドで使えないか確認
2. 実際にクラウドで実行を試行する（試さずに「ローカル必須」と書かない）
3. 失敗した場合のみ、エラー全文・試行コマンドを Issue に記録
4. problem-investigation-protocol.md の5ステップで根本原因を特定
5. それでもクラウド不可なら B カテゴリの実装 Issue を起票（ユーザー作業ではなくツール改修として扱う）
```

❌ クラウド実行を試さずに「ローカル実行が必要」と user-work Issue を作成する
❌ 「このライブラリだからクラウド不可」と試さずに決めつける（代替サービス経由の実行例あり）

## 5〜7. C / D カテゴリと恒久自律化バックログ

- **§5（C: ルール整備で自律化）**: 判断基準を明文化すれば人間不要になる事象（誤ラベル修正・完了済み Issue の自動クローズ・環境変数未設定の A 型チェックリスト適用等）。新たに発見したら実装場所（SKILL.md 手順 or コード）を明記して detail 版に追記する（desync 防止）。
- **§6（D: 外部要因）**: 課金・BAN・プラットフォーム制約は設定変更（A-6）のみユーザー作業。**影響は自律的に最小化** する（枯渇前に予告 + 枯渇後もフォールバック経路で継続）。「枯渇したので止めます」で終わらせない。
- **§7（恒久自律化バックログ）**: 「二度とユーザー確認不要」にするツール改修項目は self-improvement-loop が消化モードで進める。

プロジェクト例の詳細表はいずれも `user-confirmation-minimization-detail.md` §5〜§7 を参照。
