## ✅ 良い例

```markdown
## ✅ 完了報告

**ご依頼**: 完了報告を「PR マージ詳細」ではなく「初回指示のアウトカム中心」にするようルール・ハーネスを調整。
**できるようになったこと**: セッション完了時に依頼の再掲とアウトカムが冒頭に出るようになり、チャットを遡らずに「何を頼んで何が達成されたか」が一目で分かるようになったにゃ。

---
[PR #36](https://github.com/.../pull/36) / ブランチ `claude/...`
```

## ❌ 悪い例の典型

「PR #36 を squash でマージしました！指摘 3 件を解消、修正サイクルは 2 回でした。〇〇.md と △△.sh を更新しています」

→ 初回指示の再掲なし・アウトカムなし・プロセスとファイル名が主役。**これが「で、何頼んだっけ？」を生む**。

## §1.2 Stop フック差し戻し後の続行ターン（詳細）

判定式・アンカー・タグ別の対応表そのものは Hot 層（`completion-report-rules.md` §1.2）に常駐する。本節はその背景と機構の詳説。

### なぜ必要か（飼い主の明示指摘・2026-09-03・Issue #543）

完了報告を出してターンを終えると、Stop フック（PR 存在確認・未コミット検知・公開反映・完了報告フォーマット確認）が差し戻して **続行ターン** が始まる。クラウドの feature ブランチでは **final message を出すたびに** 差し戻される（`stop_hook_active` が防ぐのは同一 Stop 試行の直後 1 回だけ）。続行ターンで直前の完了報告を丸ごと再掲すると、ユーザーには同一内容の重複報告に見える。議論記録: 親ベース（`kai-kou/claude-code-repository-base`）側の `content/discussions/completion-report-dedup-20260903/`（本リポジトリには未同梱）。

### ハーネスのシステムプロンプトとの優先関係

「Close with a short recap that stands on its own」「Only your final message reliably reaches them」は変更できないが、Hot 層 §1.2 はその適用範囲を限定する。recap は `Stop hook feedback:` 直前の自分のターンで既に果たしており、続行ターンの読者はそのメッセージも見えている。差し戻しは recap のやり直し要求ではなく、追加手続き（または報告フォーマットの訂正）の要求である。

### 良い例 / 悪い例

```
✅（[continuation] のみ・stop-pr-check の差し戻し後）
PR #36（state=MERGED）を確認したにゃ。追加対応なし。

✅（[continuation] のみ・未コミット検知の差し戻し後に実作業をした場合）
未コミットだった設定変更をコミット・push したにゃ。

❌（同じ場面で §1 テンプレを丸ごと再掲する）
## ✅ 完了報告
**ご依頼**: …
**できるようになったこと**: …

✅（[report-format] あり・簡潔な書き直し）
## ✅ 完了報告
**ご依頼**: 〇〇の実装。
**できるようになったこと**: △△ができるようになったにゃ。
---
[PR #36](...) / ブランチ `claude/...`

✅（複合ブロック: [report-format] の行 + PR 確認要求が同一ターンに連続）
## ✅ 完了報告
**ご依頼**: 〇〇の実装。
**できるようになったこと**: △△ができるようになったにゃ。
PR #36（state=MERGED）を確認済み。   ← 未処理タスクの結果は書き直した報告に 1 行で併記（別メッセージにしない）
---
[PR #36](...) / ブランチ `claude/...`
```

### タグの届き方

`[continuation]` は `stop-router.sh` が集約メッセージの **末尾に必ず 1 回** 付ける外層タグ、`[report-format]` は `stop-completion-report-check.sh` の差し戻し行の **先頭** に付く内層タグ。判定は「`[report-format]` の行があるか」だけを見ればよい。

### ハーネス側の二重化（回数そのものを減らす）

`post-pr-confirm-mark.sh`（PostToolUse）が「セッション内で PR を確認済み」をマーカー化し、`stop-pr-check.sh` はマーカーがあれば差し戻さない。`stop-completion-report-check.sh` は「適正な完了報告済み」をセッションマーカー化し、以後の短い応答を nudge しない（判定単位が Stop イベントごとで、セッション内履歴を持たなかったことの補正）。Hot 層 §1.2 の規律はそれでも残る差し戻し（未コミット・publish-sync・フォーマット確認・プラットフォーム側 Stop フック）に対する二重防御である。

### 二重報告の根本原因と修正（#633）

**症状**: 下流リポジトリで完了報告が 2 回出る。① `✅ 完了報告`（適正）→ ② PR 監視の通知 wake で
「対応不要、PR #N は無事マージ済みで完了にゃ」等の短い受領応答 → ③ **もう一度 `✅ 完了報告`**（短い書き直し版）。

**根本原因**: `stop-completion-report-check.sh` の処理順序。#543 で入れた「このセッションで一度適正な完了報告を
出した」マーカーによる nudge 抑止が、`stop_hook_active == true` の early return より **後** に置かれていた。

```
stop_hook_active == true → exit 0        ← 続行ターンはここで抜ける
...
is_proper_report → マーカー書き込み       ← 到達しない
classify_text == nudge → hook_block
```

本ベースの標準フローは「実装完了 → Stop → `stop-git-check` / `stop-pr-check` / `stop-publish-check` の
いずれかが差し戻す → **続行ターンで完了報告を出す**」が最頻経路であり、この経路ではマーカーが常に立たない。
その後 `subscribe_pr_activity` の webhook / 通知 wake（`stop_hook_active=false`）で短い受領応答を返すと、
`classify_text` が「マージ + PR 参照 + アウトカム語なし」で nudge と判定し `[report-format]` が発火する。

**修正（2 点の多層防御・本リポジトリの `.claude/hooks/stop-completion-report-check.sh` に反映済み）**:

1. early return を **nudge 判定のスキップだけ** に限定し、マーカー記録は続行ターンでも必ず通す（主因）
2. `is_proper_report` の条件から `MERGE_RE` **だけ** を外す（`PR_REF_RE` は必須のまま維持する）。§1 テンプレートの
   完了報告は末尾に PR リンクを置くがマージ語を含むとは限らず、旧条件では「PR リンクはあるがマージと
   書かなかった完了報告」を取りこぼしていた
3. nudge 文言に「既に適正報告済みなら再掲も書き直しもしない」を明記する（ハーネスが取りこぼしても
   モデル側で止まる）

> 🔴 **`PR_REF_RE` の必須を外してはならない**（外すと #633 のセルフレビューで検出した回帰が戻る）: マーカーは
> セッション単位でタスク単位ではないため、PR に無関係なタスク（調査など）の適正報告 1 件でマーカーが立つと、
> 同一セッションの後続タスクが出した不適格なマージ報告まで nudge を素通りさせる。e2e⑦ がこれを固定している。
>
> **マーカー基準ディレクトリの `--absolute-git-dir` 化は見送った**: cwd 依存の除去を検討したが、git は
> リポジトリルートでのみ相対 `.git` を返し、サブディレクトリからは絶対パスを返す（どちらも同じディレクトリを
> 指す）ため差が出る経路を作れず、テストが vacuous になる。他のマーカー系フック（`post-pr-confirm-mark.sh` 等）と
> 同じ `--git-dir` のまま揃えてある。

回帰テストは `bash .claude/hooks/stop-completion-report-check.sh --self-test` の e2e ④〜⑦
（続行ターンでのマーカー記録 / その後の受領応答の抑止 / 続行ターンでは nudge しないこと /
PR 参照の無い適正報告ではマーカーを立てず後続タスクの不適格報告を nudge すること）。

## §4 完了・成功の定義（チェックリスト）

- [ ] 冒頭に「ご依頼（初回指示の再掲）」がある
- [ ] アウトカムが主役で、プロセス（マージ手順・レビュー往復）が主役になっていない
- [ ] PR 番号・URL・ブランチが末尾の補足 1 行に収まり、Markdown リンク記法になっている
- [ ] Slack `--outcome` も初回指示アウトカム 1 文になっている
- [ ] 依頼が複数件あった場合、**完了分が全件納品され**、未完了分はブロック要因 1 文で名指しされている（Hot 層 §3.1）
- [ ] `Stop hook feedback:` で始まる続行ターンで §1 テンプレを再掲していない（`[report-format]` があるときだけ簡潔に書き直している・Hot 層 §1.2）
