# ユーザー指示の Issue 化ルール

ユーザーから作業指示を受けたとき、**Claude が自律的に Issue を作成して記録する** ためのルール。
過去の指示・対応履歴を Issue で追跡可能にし、コミット履歴や PR を遡るコストを削減する（CP-6）。

> **原則**: Issue は「なぜ変更したか」を記録する唯一の場所。コミットメッセージは「何をしたか」を書くが、
> 「ユーザーがどういう意図で依頼したか」は Issue にしか残らない。

## 前段: それは「質問」か「指示」か（入力の分類）

**質問されたら答える。実装しない。** 「X を使うべき？」は「すべてを X に移行せよ」ではなく、「Y を追加するには何が要る？」は「Y を追加せよ」ではない。**疑問形の入力で判断がつかないときは質問と仮定し、まず答える**（実装は「進めて」と言われてから着手する）。ただし **日本語の丁寧な依頼表現**（「〜してくれない？」「〜してもらえますか」「〜できますか」）は文法上は疑問文でも **指示として扱う** — 本節が対象にするのは「可否・要否・方法を問う疑問文」だけである。答えたうえで「やるなら A か B」まで示せば、ユーザーは 1 往復で選べる。

> **射程はここだけ**（軸を混同しない）: 本節が扱うのは **入力そのものが疑問形かどうかという分類** に限る。**指示だと分類した後**、その指示文の内部に曖昧さがあった場合は従来どおり `user-confirmation-minimization.md` §3 item 0 が適用され、**最も単純な合理的解釈で仮定を立てて自律実行する**（そこで質問側に倒すのは CP-1/CP-6 違反）。既に Issue 化して着手済みのタスクにも本節は適用しない。

## Issue 化の判断フロー

```
ユーザー指示を受信（上記の前段で「指示」と分類済み）
  ↓
ファイル変更・コード変更・設定変更を伴うか？
  ├── No → 純粋な質問・説明・確認のみ → Issue 化不要（即回答）
  └── Yes ↓
        作業完了に 5 分以上かかるか / 複数ファイルに影響するか？
          ├── No（明らかな1行修正・誤字修正等）→ Issue 化不要（即実行して完了報告）
          └── Yes → ① Issue 作成 → ② `status:in-progress` 付与（CP-4 論理ロック）
                    → ③ 作業ブランチで実装 → ④ PR → セルフレビュー → 自動マージ
                    → ⑤ Issue クローズ（PR 本文に `Closes #N`）
```

**Issue 化が必要**: コード・スクリプト変更 / ルール・設定変更（CLAUDE.md・`docs/rules/*.md`・`settings.json`）/ スキル追加・改修 / 新機能・改善依頼（「〜できるようにして」）/ バグ修正依頼（「〜が動かない」）/ ドキュメントの新規作成・大幅更新 / 複数ファイルにまたがる変更。

**Issue 化不要**: 純粋な質問・調査（ファイル変更なし）/ 動作確認・レビューのみ / 自明な 1 行修正（誤字・1 ファイル 1 箇所 30 秒以内）/ セッション内の一時的なコマンド実行。

> **迷ったら Issue 化する**。Issue 作成コストは低く、記録がないことのコストは高い。

## タイトル・ラベル規約

タイトルは `feat:` / `fix:` / `improvement:` / `docs:` のいずれかのプレフィックス + 概要（プロジェクト固有の制作系は `[{ID}] {Phase}: {概要}`）。

必須ラベル: `type:feature` | `type:bug` | `type:improvement` | `type:docs` のいずれか + **`status:in-progress`**（作業開始時に即付与・CP-4 論理ロック）+ **`sp:N`**（1/2/3/5/8・基準は `session-sprint-rules.md` §3。done_sp 計測のため省略禁止）。

## Issue 本文テンプレート

```markdown
## ユーザー指示

{ユーザーから受けた指示の内容（原文に近い形で記録。所感を命令形に書き換えない・L-113）}

## 対応方針

- {何をするか（箇条書き）}

## 完了条件

- {何ができたら完了とするか（検証可能な形で）}
```

作成は `mcp__github__issue_write`（クラウド一次経路）または `gh issue create --label "..."`。実例は `user-instruction-issue-rules-detail.md`。

## 禁止パターン

- ユーザーが「Issue にして」と言わないと Issue を作らない（このルール違反）
- Issue を作らずにコミットだけする（追跡不能）
- Issue タイトルに「ユーザーに言われたから」と書く（自明なため不要）
- 質問・確認のたびに Issue を作る（記録不要なケース）

> **適用範囲**: 本ルールは **ユーザーが直接発した指示** にのみ適用する。スケジュールタスク・自律実行パイプラインは各スキル（SKILL.md）内の Issue 管理フローに従う。
