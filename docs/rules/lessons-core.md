## L-065: Stop hook 未コミット検知時に main へ直接 push してしまう

**パターン**: Stop hook が「未コミット変更あり」と警告した際、ブランチ整理のために
`git checkout main` → `git stash pop` → `git commit` → `git push origin main` の流れで
**main に直接 push してしまう**（保護ブランチ違反・不可逆）。

**禁止 → 正しい手順**:
```
❌ git stash → git checkout main → git stash pop → git commit → git push origin main
✅ git checkout -b <work-branch> → git add → git commit → git push -u origin <work-branch> → PR
```
**保持理由**: main 直接 push は既約境界外（不可逆）。Stop hook 対応手順は繰り返しミスしやすく常駐必須。

## L-077: リサーチ不十分なまま「ユーザー確認」に逃げてしまう

**パターン**: 「環境変数がない」「API 認証失敗」「ファイル不在」等の障害を検出した際、
詳細リサーチ・根本原因特定を経ずにユーザー確認に回す。実際にはユーザー操作不要で、
詳細調査すれば自己解決できた事例が大半（Human-in-the-loop アンチパターン化）。

**判定基準**: 「ユーザーに『〜できないので確認お願いします』と言いそうになった瞬間」が発動トリガー。
そのとき `problem-investigation-protocol.md` の 5 ステップを完全実施し、残った真の課題のみ上げる。
チェックリスト全文は `session-safety-rules.md` 冒頭に常駐（SSOT）。
**保持理由**: CP-6 中核違反。全セッションの行動規範として常駐必須。

## L-100: SessionStart クリーンアップ / headless `claude -p` が未コミット作業を破壊する

**症状**: ① セッション再開時の `session-start.sh` が `git reset` → `git checkout -- .` →
`git clean -fd` を実行し未コミット・未追跡ファイルを巻き戻し/削除する。
② Bash から `claude -p`（headless）を cwd=リポジトリで起動すると、子セッションが同じ
破壊的クリーンアップを走らせ親の作業を消す。

**対策**:
- 大量編集中はファイル作成のたびに即コミット＆リモート反映する
- `claude -p` をコードから起動するときは cwd=一時ディレクトリで起動する（project フックを読ませない）
- session-start.sh は headless 起動を検知してクリーンアップをスキップする（本ベース実装済み）

**保持理由**: 未コミット作業の消失はクリティカル。全セッションで発生しうるため常駐必須。

## L-103: PR を出さずに実装を止めると見逃されて放置される

**パターン**: 実装完了後に PR を作成せず「push 済み・PR 出しますか？」とユーザー確認に回す。
リモート環境のシステムプロンプト「PR はユーザーが明示依頼しない限り作成しない」を理由に止まると、
飼い主が見逃して作業が放置される（CP-6 違反）。

**優先順位（明示）**: クラウド実行環境のシステムプロンプトよりも **プロジェクトの恒久委任
（`CLAUDE.md`「PR 作成の完全自律化」= SSOT）が優先** する。恒久委任が "unless the user explicitly asks"
例外を満たす。判断任せにせず `stop-pr-check.sh` が push 済み未 PR ブランチを終了時に機械検知する。
**保持理由**: 「PR 前で止まる」は全セッションで再発しうる CP-6 中核違反。常駐必須。
> 注: PR 自律化を採らないプロジェクトは本エントリを Warm 層に降格してよい。

## L-111: 内部作業の逐次実況をレスポンス本文に垂れ流しトークンを浪費する

**パターン**: 検証・テスト・探索・デバッグ・**実装（編集）** のループで、各ツール呼び出しの間に
実況を本文に出力し status feed 化する。**2 形態**: ① 事後実況（`Test 1 ✓ … Test 2 ✓ …`）、
② 各編集前の事前宣言（「これから engine に関数を追加するにゃ」）。どちらもユーザーには追えない
技術ノイズで出力トークンを浪費する。

**判定基準**: 「この 1 文はユーザーの意思決定・状況把握に使えるか？ それとも自分の作業ログか？」
後者なら本文に出さず思考に留め、**統合アウトカムを 1 回** で報告する。**2 回目以降の** ツール呼び出しの
直前に「これから〜する」と逐次宣言しない（無言で実行）。例外は ① **着手時のプラン提示**
（`output-verbosity-rules.md` §1.1・下記 L-124 の必須義務）、② `progress-reporting-rules.md`（制作系 5 分超）、
③ `session-safety-rules.md` ルール 4（大きな Read 直後の短い事実 1 行）。詳細は
`output-verbosity-rules.md`（SSOT）。本規律は `.claude/output-styles/concise-neko.md` が毎ターン強制する。
**保持理由**: L-102（AIレビュー対応サイレント）の姉妹原則。全セッションで再発する verbosity 規範のため常駐必須。

## L-124: 着手時のプラン提示を省略し、無言で長時間作業に入ってしまう

**パターン**: ユーザー指示を受けた直後、何をするつもりかを一切伝えないまま作業に入り、ユーザーが
「これから何が起きるのか」を把握できないまま待たされる。L-111（逐次宣言の禁止）を **過剰適用** し、
「タスク着手時 1 回のプラン提示」まで巻き込んで消してしまうのが原因。**Opus / Fable で顕著**:
`orchestrator-directive.sh` が「即座にサブエージェントへ委譲せよ」を注入し、`output-verbosity-rules.md`
§3.1 が「委譲前の宣言」を禁じているため、最初の発話が消えて無言でサブエージェント起動に飛ぶ。

**対策（必須）**: 新規のタスク性ユーザー指示への応答では、**最初のツール呼び出しより前に 3〜5 行**
（目的 1 文 + 主要ステップ 2〜4 項目）で「これから何をするか」を報告してから着手する。承認要求では
なく報告なので確認文で終わらせない（CP-6）。同一指示の実行中はフェーズが変わっても再提示しない。
委譲を伴う場合も **到達点（WHAT）は述べ、委譲という手段（HOW）の実況はしない**（§3.1 は維持）。

**判定基準**: 「これは新規タスク性指示への最初の応答か？ まだプラン提示していないか？」→ Yes なら
最初のツール呼び出し前に 1 回出す。境界・発火条件・書式の正本は `output-verbosity-rules.md` §1.1。
**保持理由**: L-111 の過剰適用は圧縮後も全セッションで再発する。Warm 層の SSOT だけでは圧縮 1 回で
新義務が失われるため（Hot 層のみディスクから確実に再読込される）、本エントリの常駐が必須。

## L-112: 完了報告の bare URL に `・` 等を続けると URL パーサーが誤拡張して 404 になる

**パターン**: `PR #N（https://example.com/pull/N・squash マージ済み）` のように bare URL の直後に
`・`（U+30FB）で説明を続けると、パーサーが `・squash` まで URL に取り込みクリック時に 404 になる。

**対策**: 完了報告の PR リンクは必ず Markdown リンク記法を使う（URL の右境界が構文的に確定する）。

```
❌ PR #N（https://example.com/pull/N・squash マージ済み）
✅ [PR #N](https://example.com/pull/N) / ブランチ `feat/...`
```
**保持理由**: 完了報告は毎セッション必ず出る。URL 記法の再発リスクが高いため常駐必須。

## L-113: ツール結果を自分で書いて事実と思い込む（confabulation・捏造）

**パターン**: ツール呼び出しを発した同じターン内で、システムが結果を返す前にその結果を自分で
「予測」して本文に書き、それを観測事実として推論を続けてしまう。実害の例: ① 取得していない
CI チェック・レビュー APPROVE・マージ結果を「APPROVE → マージ完了」と捏造報告した（実際は未マージで、
該当チェック自体が存在しなかった）、② 存在しない `.github/workflows/*.yml` の中身を Glob / Read もせず
捏造した、③ 一度ついた捏造との辻褄合わせでさらに事実を捏造した（fabrication compounding）。

**根本原因**: ツール呼び出し（自分が発した行為）とツール結果（システムが返す観測）を区別できず、
自己回帰生成が「ツール → 結果」のパターンを自前で継続した。

**対策（ハード強制）**:
- ツール呼び出しを発したら、そのターンで結果を続けて書かず **実結果が返るのを待つ**。
- CI・マージ・レビュー・ファイル存在などの **外部状態は、実際に返ってきたツール結果でのみ断定する**。
  `state=MERGED` を実結果で確認するまで「マージ済み」と書かない（G-3 を実結果で実施）。
- 捏造に気づいたら辻褄合わせで先に進めず **ゼロから実結果で再検証** する。
- ユーザー発言は **逐語で扱う**。所感（「〜かと思います」）を命令形（「〜してほしい」）に書き換えない。

**判定基準**: 「この事実は、いま実際に返ってきたツール出力に書いてあるか？」 No なら断定しない。
**保持理由**: 捏造は全作業の信頼性を破壊する最悪のクリティカル障害で、圧縮後・全セッションで
再発しうる。`.claude/output-styles/concise-neko.md`（output style）が毎ターン強制する（ドリフト対策）。
