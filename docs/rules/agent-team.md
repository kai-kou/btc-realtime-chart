# サブエージェント・エージェントチーム活用ルール

タスク対応時は積極的にサブエージェント（Agent tool）を活用し、並列実行で効率を最大化する。

## 基本方針

- 独立した作業は **並列サブエージェント** で同時実行する。逐次処理より並列処理を優先する
- 調査・リサーチ系タスクはリサーチ専任のサブエージェント（Agent tool の `subagent_type=Explore`）に委譲し、メインエージェントは結果の統合と判断に集中する
- 複雑な実装計画は設計・プランニング専任のサブエージェント（Agent tool の `subagent_type=Plan`）に先行して検討させ、その成果をもとに実装タスクを分割する

## 2つの協調モード（fan-out vs 議論型）と用語整理

本ドキュメントが扱う「エージェントチーム」は、歴史的に **役割分担型 fan-out**（各サブエージェントが独立評価 → メインが集計・議論なし）を指してきた。これは Claude Code 公式の **Agent Teams 機能**（`SendMessage` による peer-to-peer・実体は別 Claude Code インスタンス）とは別物である点に注意する（`TeamCreate` / `TeamDelete` は v2.1.178 で廃止済み・§F-7）。

| モード | 実体 | エージェント間通信 | 用途 | 参照 |
|--------|------|------------------|------|------|
| **役割分担型 fan-out**（既定） | Agent tool の並列サブエージェント | なし（メインが集計） | 多角的な独立チェック・速い | 本ドキュメント |
| **議論型（敵対的相互レビュー）** | **ネイティブ Agent Teams**: メイン = lead、参加者 = name 付き background `Agent` + `SendMessage` 再開 + 共有ホワイトボード | あり（ホワイトボード経由で相互に読み反論） | 過剰指摘の相互排除・合意形成・根本原因特定 | `.claude/skills/discussion-review/SKILL.md`（既定）・`docs/rules/discussion-whiteboard-rules.md`。フォールバック: `tools/run_discussion_review.py`（claude -p 駆動） |

> **使い分け（SSOT は `agent-team-summary.md`「2 協調モードと振り分け」）**:
> - **ユーザーが明示的に「専門チームを組成して」「専門チームで」「チームで議論して」等と指示したら、議論型（`discussion-review` スキル）を既定とする**（飼い主決定）。fan-out で代替してよいのはコスト/速度優先の明示か軽微タスクのときだけ（理由を 1 行述べる）。
> - 内部の自動調査（`problem-investigation-protocol.md` Step 3 の障害調査）・定型チェックは fan-out が既定（軽量・速い）。
> - **過剰指摘や誤検知が問題になるレビュー**（画像/台本レビュー等）も議論型を選び、各エージェントに互いの指摘を批判検証させて critical を相互検証済みに絞る。
>
> **ツール露出の変遷**: 旧実機検証（#2588）では `Workflow`/`TeamCreate`/`SendMessage` が claude -p サブプロセス内でのみ利用可能だったが、**2026-07 時点でメインセッションに `Workflow`（2026-07-03 確認）・`SendMessage`（deferred ツール・2026-07-11 実測）が露出**。name 付き Agent 起動で暗黙チームが成立するため `TeamCreate` は不要（v2.1.178 で `TeamCreate` / `TeamDelete` 自体が廃止され、`team_name` は無視される）。ただしサブエージェント側の共有タスクボード（TaskCreate 等）は利用不可・SendMessage の配達は受信側ターン継続中のみ（実測 V-5・詳細は開発リポジトリの提案記録 §1 に保持）。委譲が空回答・期待外になる公式要因は §F-1〜F-7 を必ず確認する。

## Phase別の並列化パターン

> ⚠️ 以下の表は **出自プロジェクト（動画制作パイプライン）の実例**。自プロジェクトのワークフローの
> 各フェーズに読み替えること（「独立した作業を並列サブエージェントで同時実行する」原則が本体）。

| フェーズ / タイミング | 並列化の例 |
|-------------------|-----------|
| Phase 1（ネタ収集） | 複数ニュースソースの巡回を並列エージェントで同時実行 |
| Phase 2（リサーチ） | リサーチ結果のファクトチェックと網羅性チェックを並列実行 |
| Phase 3（台本制作） | **セクション単位で分割生成**（2〜3セクションずつ並列サブエージェント）→ メインが統合。品質チェックも並列 |
| Phase 4（素材制作） | 音声合成・画像生成・動画素材取得を並列エージェントで同時進行 |
| Phase 5（動画制作） | レンダリング後の自動レビュー項目（尺・同期・無音区間）を並列チェック |
| 各PhaseのPR作成後 | AIレビュー依頼（Gemini / Copilot）を並列で送信 |

## エージェントチーム構成の例

複数工程にまたがるタスクでは、以下のようにエージェントチームを編成する。

```
メインエージェント（オーケストレーション）
├── Explore エージェント（コードベース調査・ファイル探索）
├── 実装エージェント A（ファイル編集・コード生成）
├── 実装エージェント B（別ファイルの並行編集）
└── 検証エージェント（テスト実行・品質チェック）
```

## 使い分けガイドライン

| 状況 | 推奨アプローチ |
|------|--------------|
| 単一ファイルの軽微な修正 | サブエージェント不要。直接対応 |
| 複数ファイルの調査が必要 | `Explore` エージェントに委譲 |
| 独立した2つ以上の作業 | 並列サブエージェントで同時実行 |
| 大規模な実装タスク | `Explore` (必要に応じて) → `Plan` → 並列実装エージェント → 検証エージェント |
| ファイル探索 + 実装が必要 | Explore で調査 → 結果を受けて実装（逐次） |

## 🔴 委譲が「空回答・期待外の回答」になる公式要因（#367・2026-07-29 検証・v2.1.220）

サブエージェント / Agent Teams の回答が空になる・意図しない形式で返る現象は、**モデルの怠慢ではなく
ハーネスの仕様** で説明できるものが大半である。委譲前に以下を確認する。

### F-1. ツールプールの 2 段フィルタ（空回答の最大要因）

サブエージェントのツールは 2 段のフィルタで削られ、**削除はエラーを報告しない**（silent）。
`tools` に書いたツールが全滅すると zero tools となり、**空・意味不明な回答** になる
（v2.1.208 以降は起動拒否のエラー）。

| フィルタ | 対象 | 除去されるもの |
|---------|------|--------------|
| 第 1（全サブエージェント） | 常に | `Agent`（深さ上限時）/ `AskUserQuestion` / `EndConversation` / `EnterPlanMode` / `ExitPlanMode`（`permissionMode: plan` 以外）/ `ScheduleWakeup` / `TaskOutput` / `WaitForMcpServers` / `Workflow` |
| 第 2（background 実行） | **v2.1.198 以降は background が既定** | 下記の許可リスト **以外の組み込みツール全部**（MCP ツールは全て残る） |

background で残る組み込みツール: `Read` `Grep` `Glob` `Bash` `PowerShell` `Edit` `Write` `NotebookEdit`
`WebFetch` `WebSearch` `TodoWrite` `Skill` `ToolSearch` `EnterWorktree` `ExitWorktree` `Monitor`
`TaskStop` `SendMessage` `Artifact`。Agent Teams の teammate はこれに加えて `TaskCreate` `TaskGet`
`TaskList` `TaskUpdate` `CronCreate` `CronDelete` `CronList` を保持する。

- **同じ定義でも foreground と background で解決結果が変わる**（`tools` に書いても background では消える）。
- `tools` が MCP ツールのみの定義は、MCP 未接続の headless / cron 実行で zero tools になりうる
  （`Read` 等の組み込みを 1 つ以上足しておく）。
- 機械検出: `python3 tools/check_agent_definitions.py`（`.claude/agents/*.md` 変更時に
  `tools/self_review_check.py` が自動実行する）。

### F-2. `Explore` / `Plan` は CLAUDE.md を読まない

組み込みサブエージェントのうち **`Explore` と `Plan` だけが CLAUDE.md と親の git status をスキップ**
する（速度・コスト優先の公式仕様。frontmatter でも設定でも変更できない）。他の組み込み・カスタム
サブエージェントは読む。

→ プロジェクトのルール（応答言語・出力フォーマット・除外ディレクトリ等）を守らせたいなら、
**委譲プロンプトに再掲する**。「CLAUDE.md に書いたから従うはず」は Explore / Plan には通用しない。

### F-3. output style はサブエージェントに継承されない

サブエージェントは自前のシステムプロンプトで動くため、**セッションの output style は返答を規定しない**
（唯一の例外は fork）。本ベースの `concise-neko`（日本語・ねこ口調・サイレント規律）も **届かない**。

→ 返答の言語・形式に要件があるなら、委譲プロンプトに明示する（「日本語で返す」「JSON のみ返す」等）。

### F-4. 「最終テキスト = 親への返り値」であることを明示する

サブエージェントの最終テキストがそのまま親への返り値になる。本ベースは「内部作業はサイレントに・
実況を出さない」（L-111）を全体規律にしているため、**この規律を委譲先が過剰適用すると返り値そのものが
痩せる**。委譲プロンプトには「最終テキストは親への返り値なので、結論・根拠・該当箇所を必ず含める」
（= サイレント規律の適用外）を書く。

### F-4b. 委譲プロンプトは「context pointer」として書く（F-1〜F-4 の一般原則）

F-1〜F-4 は「何が起きるか」の記録だが、**どう書けば起きないか** の一般原則が無かった。委譲プロンプトの
各行は **context pointer**（コンテキスト外の材料を名指しし、そこへ到達すべき条件を符号化した参照）
であり、到達の信頼性を決めるのは **参照先ではなく参照の書き方** である。届いてほしい材料が届かないときは、
まず **書き方を研ぐ**。それでも駄目なときに初めて材料を本文へ展開する（順序を逆にすると、研げば済んだ
ものを毎回コピーして運ぶことになる）。

pointer が担う仕事は 2 つ。**何を指すか** を述べ、**どの分岐で到達すべきか** を列挙する。

- **先頭語に仕事をさせる**: 判定は前から行われるので、発火条件を決める語を先頭に置く
- **1 分岐 1 トリガー**: 同じ分岐を同義語で二度書かない（分岐が増えたように見えるだけで精度は上がらない）
- **本文が既に持つ身元情報は削る**: 参照先の中で自明なことを参照側で繰り返さない
- **禁止形で操縦しない**: 禁止は禁止対象を文脈に持ち込み、かえって選ばれやすくする。**やってほしい形を
  述べる**（「所感を書くな」ではなく「結論・根拠・該当箇所を書く」）。言い換え不能なハードガードレールに
  限って禁止形を使い、その場合も positive を併記する

これは F-2（`Explore` / `Plan` は CLAUDE.md を読まない）・F-3（output style は継承されない）・
F-4（最終テキストは親への返り値）が個別に要求している再掲を、**なぜ再掲が要るのか** という一つの
説明にまとめたもの。委譲先にとって、親のコンテキストは「pointer の先の材料」ですらなく最初から無い。

### F-5. 空回答を観測したら API エラーを疑う

- **foreground**: レート制限・過負荷・サーバエラーに切られた場合、テキスト出力済みなら **部分出力 + 打ち切り注記** が返る。
  **何も出力していない / ツール呼び出しだけだった場合は `Agent terminated early due to an API error`**（v2.1.200 以降）。
  v2.1.199 では打ち切り注記だけの **空の partial result** が返っていた。
- **background**（既定）: サブエージェントが **failed とマークされ**、終了時のメッセージに API エラー名と
  最後の出力が含まれる（部分作業は失われない）。

→ 空回答は「サブエージェントが何もしなかった」ではなく API 側の打ち切りであることが多い。再委譲で回復する。

### F-6. `Explore` のモデルは main 会話を継承する（v2.1.198 以降）

`Explore` は以前「常に Haiku」だったが、**現在はメイン会話のモデルを継承** する（Claude API では Opus 上限）。
「Explore に投げれば安い」という前提は成り立たず、`Agent` ツールの `model` 指定でも組み込みの継承は変わらない。

→ 安く保ちたいなら **`.claude/agents/` に `Explore` という名前のサブエージェント定義を置き、
`model: haiku` を指定して組み込みを上書きする**（公式明記: user / project スコープの `Explore` は
組み込みを上書きし、自分の `model` フィールドを保つ）。
上書きしない場合はメイン側の model / effort を下げる。なお **上書き版が CLAUDE.md を読むかは公式に記載がない**
ため、F-2 のとおり必要なルールはプロンプトに再掲する前提で設計する。

### F-7. Agent Teams（v2.1.178 以降）の制約

- `TeamCreate` / `TeamDelete` は **廃止**。`Agent` の `team_name` は受理されるが **無視** される
  （name 付き Agent の起動で暗黙チームが成立する）。
- **in-process teammate は background サブエージェントを起動できない**（`run_in_background` や
  `background: true` は **エラー**）。teammate の子作業は foreground で走る。
- **nested team 不可**（teammate は teammate を spawn できない。チーム管理は lead のみ）。
- `/resume` / `/rewind` で in-process teammate は復元されない（lead が存在しない teammate に話しかける）。
- サブエージェント定義を teammate として使うと、`skills` / `mcpServers` frontmatter は **適用されない**。
- teammate の mailbox は `~/.claude/teams/{team}/inboxes/{agent}.json`。不正エントリがあると
  v2.1.207 未満では配達がブロックされる（現在は不正エントリのみ除去される）。
- `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` が **必須**（未設定ならチームは組成されず、Claude は
  黙って通常のサブエージェントにフォールバックする）。本ベースは `.claude/settings.json` の `env` で設定済み。

> **深度の履歴（一般サブエージェント・#375）**: `Agent` を teammate 以外のサブエージェントから使う場合の
> ネスト可否は §F-9 の深度上限に従う（v2.1.172〜216 は 5 層固定 → v2.1.217〜218 は 1 層 → **v2.1.219 以降は 3 層が既定**）。
> 上記の「nested team 不可」は Agent Teams（teammate）固有の制約であり、通常のサブエージェントのネストとは別軸。

### F-8. 完了報告が出ない最大要因は「完了通知が後のターンに届く」こと（v2.1.211・#375）

background 実行（v2.1.198 以降の既定）では、**サブエージェントの結果は完了通知として後のターンに届く**。
公式逐語（`sub-agents` / Run subagents in foreground or background）:

> A background subagent's results reach Claude as a completion notification in a later turn.
> Claude waits for that notification before reporting the subagent's results, and if you ask about
> progress first, it reports that the subagent is still running.

→ **「サブエージェント側が完了している」ことと「親が報告できる」ことは同期しない**。委譲した直後のターンで
結果を語れないのは仕様であり、モデルの怠慢でも取りこぼしでもない（v2.1.211 より前は未完了の結果を
報告してしまうことがあり、その捏造を止めるために待つ設計に変わった）。

**使い分け（委譲時に必ず選ぶ）**:

| 必要なもの | 指定 |
|-----------|------|
| そのターン内で結果を使って続きを書く（要約・判断・実装の前提） | `run_in_background: false`（同期実行） |
| 並列に走らせて後で回収する（独立調査・長時間タスク） | 既定（background）。通知が届くまで結果を断定しない |
| 定義として常に background にしたい | サブエージェント frontmatter `background: true`（未設定なら Claude が選び、既定は background） |
| セッション全体で同期実行に固定したい | `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`（fork モードにも優先する） |
| スキル（`context: fork`）を同期に戻したい | スキル frontmatter `background: false`（v2.1.218 で fork スキルが background 既定になった） |

> ⚠️ **サブエージェント frontmatter の `background` は「`true` で常に background」だけが公式に定義されている**。
> 同期化の手段として `background: false` を当てにしない（同期にしたいなら `run_in_background: false` か
> `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`）。`background: false` が明記されているのは **スキル** の frontmatter。

- 完了済みサブエージェントは **`/tasks` に done として残る**（v2.1.208 以降。以前は完了と同時に消えた）。
  「終わったはずなのに見当たらない」ときの一次確認先。
- **`SendMessage` で完了済みサブエージェントは再開できる**（`Agent` の再起動不要・background で auto-resume）。
- 通知を待たずに「完了しました」と書くのは L-113（confabulation）そのもの。**実結果でのみ断定する**。
- **報告そのものはサイレント規律（L-111）の対象外**。委譲結果の統合報告は「作業ログ」ではなく
  ユーザー向けアウトカムであり、抑制してはならない（`output-verbosity-rules.md` §3.1）。

**「待つ」の作法 — 手段を問わずポーリング禁止（#648）**

親が「待つ」とは **そのターンを終えること** であり、同一ターン内で完了を確認し続けることではない。
完了通知はハーネスが **後のターンとして** 届けるため、待機のための能動的な確認は原理的に空振りしかせず、
ツール呼び出し・出力トークン・コンテキストだけを消費する。

| ❌ しない | ✅ する |
|---|---|
| `sleep` ループで待つ | 委譲後は残りの独立作業を進め、無ければ **ターンを終える** |
| `ReadNotifications` を繰り返し呼んで完了を探る | 「通知が pending」とシステム通知が告げたときだけ呼ぶ（**一次情報はハーネスのツール定義**「Call this as soon as a system notice says notifications are pending」。待機ポーリング用のツールではない）※ 公式 Docs にも §F-1 の表にも本ツールは現れないが、前者は未掲載、後者は **サブエージェント側のツールプール** の表であり、本ツールはメインセッションに提供される通知受信ツールなので軸が違う（#648 で実機確認） |
| `TaskGet` / `TaskOutput` / `/tasks` を進捗確認のため連打する | `/tasks` は「終わったはずなのに見当たらない」ときの **一次確認 1 回** に限る |
| 「完了待機中」等のテキストを出して同じ確認を繰り返す | 待機の実況を出さない（L-111・`output-verbosity-rules.md` §2） |

**タイムアウトを理由にポーリングしない**: サブエージェントの完了通知はハーネス内イベントであり、
`tools/pr_review_heartbeat.sh` が対象とする外部イベント待ち（`subscribe_pr_activity`）のハートビートとは別物。
待機ターンを埋めるための出力・確認は不要。

**例外（能動確認してよい唯一の場面）**: 呼び出し側スキルが定める **無応答判定** に達したときの状況確認 1 回
（議論型レビューなら `.claude/skills/discussion-review/SKILL.md`「3. ガードレール」1 項・目安 10 分。判定は
経過時間の監視ではなく「他の参加者が揃ったのに 1 名分だけ届かない」状態で行う）。これも「完了したか」を
探る確認ではなく `SendMessage` による生存確認であり、繰り返さない。

### F-9. 3 種類の上限（超過は spawn 失敗として返る・#375）

| 上限 | 既定 | 環境変数 | 超過時のエラー |
|------|------|---------|--------------|
| 同時実行数 | 20（v2.1.217〜） | `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` | `Concurrent subagent limit reached`（再試行しないよう指示される） |

### Adaptive Thinking（適応的思考）

Opus 5 / Opus 4.8 / Opus 4.7 / Opus 4.6 / Sonnet 5 は **Adaptive Thinking** を搭載。クエリの複雑さに応じて、内部で「どれだけ考えるか」を自動調整する。Opus 5 / 4.8 / 4.7 は **adaptive 固定**（固定 thinking budget は使えない・`CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING` は無効）。Opus 5 は adaptive が **既定 ON**（未指定でも思考する）。

- 単純なタスク → 思考を最小化（速く・安く）
- 複雑なタスク → 深く考える（品質優先）
- **`/effort` コマンド** で明示的に制御可能（CLI のみ。ブラウザ版はステータスバーのドロップダウンで変更）。5段階（v2.1.105+）:
  - `/effort low` — 速度優先（定型チェック・軽量タスク）
  - `/effort medium` — トークン節約（API デフォルトより低負荷）
  - `/effort high` — 複雑なタスクに対応
  - `/effort xhigh` — **現行 Opus / Sonnet では明示指定が必要**（既定は `high`）。コーディング・エージェント・台本生成に推奨
  - `/effort max` — 絶対最大（現行 Opus / Sonnet・Fable で利用可）。correctness がコストより重要な時のみ
  - （Opus 系セッション限定）`ultracode` — xhigh + Dynamic Workflows（`/workflows`）。大規模・多エージェントの動的オーケストレーション。`settings.json` には書けない

### Interleaved Thinking（ツール呼び出し間の思考）

Claude 4 モデル全般で対応。ツール結果を受け取った後に内部思考を挟めるため、**マルチステップのエージェント動作** で品質が向上する。

- multi-agent pipeline の精度向上に活用
- 特に `script-pipeline` / `audio-pipeline` で顕著な効果が期待できる

### コスト最適化の優先順位

> **原則: 知能天井を下げるレバーは最後に引く**（Anthropic cookbook [Cost Optimization on the Claude API](https://github.com/anthropics/claude-cookbooks/blob/main/cost_optimization/cost_optimization.ipynb) の適用順序を採用・議論記録は `content/discussions/cost-optimization-cookbook-adoption/`）。
> キャッシュ・入力/出力トークン管理は「同じ知能で払う額」を減らすが、モデル変更と effort 低下は「できることそのもの」を減らす。前者を使い切ってから後者を検討する。
>
> **per-token 価格 ≠ per-task コスト**: 安いモデルがターン数・やり直しを増やせば総額は上がりうる。削減率は「1 タスクを完了するまでの総コスト」で読む（下表の削減率はすべて per-token ベースの目安）。

上から順に検討する（上ほど品質を犠牲にしない）。

| 順位 | 戦略 | 本リポジトリでの可否 | 削減効果 | 適用タイミング・注意 |
|---|------|------|---------|-------------|
| 1 | **Prompt Caching（TTL 延長）** | ⭕ `ENABLE_PROMPT_CACHING_1H=1` を `env-vars.md` で **推奨**（実際に設定されているかは環境ごとに要確認。本ベースの `.claude/settings.json` には未設定） | — | サブスクでは既定 1 時間、Usage Credits 利用中は 5 分に落ちるため本 env で 1 時間を維持する（[公式](https://code.claude.com/docs/en/costs)）。**`cache_control` を message 単位で配置する制御は API 直叩き専用で本リポジトリからは不可**（`claude-api-usage-rules.md`）。cookbook の「最大 90% 削減」は explicit breakpoint 前提の実験値であり、本リポジトリの実測ではない |
| 2 | **コンテキストを小さく保つ** | ⭕ Hot/Warm 層階層化・CLAUDE.md 圧縮・無関係タスク間の `/clear` | — | `token-optimization-rules.md` が SSOT。長時間セッションは会話全文を毎リクエスト送るため、コンテキスト量がそのまま単価になる |

| 5 | **Haiku を使う（最後の手段）** | ⭕ `Agent` の `model` | 60〜80% 削減（vs Opus・per-token） | 調査・検証・チェック系で **かつ品質バーを確認できている場合のみ**。ターン数増加で相殺されうる（per-task で評価する） |

> **議論型レビュー・Agent Teams のコスト**: teammate は各自のコンテキストを持つため、プラン実行時で標準セッションの約 7 倍のトークンを使う（[公式](https://code.claude.com/docs/en/costs)）。チームは小さく保ち、teammate は sonnet を既定にし、役目が終わったら終了させる。

#### 委譲先の出力トークンを抑える（早期撤退マーカー）

`agent-team-summary.md` の Haiku 向けテンプレート末尾にある `<CANNOT_COMPLETE: 理由1行>` は、cookbook の stop sequence sentinel（処理不能を悟った時点で定型マーカーだけ吐かせ、生成を止める）の翻案にゃ。`stop_sequences` API パラメータは本リポジトリから使えないため、**プロンプト側の指示** として実装している。処理不能なサブエージェントが「なぜできないか」の長文を書いて出力トークンを燃やすのを防ぐのが目的で、親側はこのマーカーを見たら再委譲せず自分で原因を切り分ける。

**メインセッション** :
- デフォルトは **Sonnet 5** を使用する
- 長文生成や複雑な設計判断が必要な場合は **`/model opus`** に切り替える（バージョンは書かない）
- 現行の Opus / Sonnet はともに **1M トークン** のコンテキストウィンドウを持つため、長時間パイプラインでも圧縮が発生しにくい（Claude Code では Max/Team/Enterprise プランで 1M に自動アップグレード）

**サブエージェント** （Agent tool の `model` パラメータで指定）:
- `subagent_type=Explore` → **モデルはメイン会話を継承する**（v2.1.198〜。`model` 指定では下げられない。
  安く保つなら §F-6 のとおり `Explore` という名前の project サブエージェント定義で上書きする）
- `subagent_type=Plan` → `model="sonnet"` （実装計画・設計）
- `subagent_type=general-purpose` （実装） → `model="sonnet"`
- `subagent_type=general-purpose` （検証・チェック） → `model="haiku"`

**Haiku 推奨スキル**（`project-sync` / `retro-try-handler` / `theme-discovery` は SKILL.md frontmatter に `model: haiku` を設定済み。`sns-publisher` はフェーズ混在のため frontmatter ではなく本文セクションでモデル使い分けを定義）:

| スキル | Haiku 適用範囲 | 理由 |
|-------|--------------|------|
| `project-sync` | 全フェーズ（frontmatter に設定） | Issue/PR 状態の定型チェック・ラベル更新のみ |
| `retro-try-handler` | 検出・ルーティングフェーズ（frontmatter に設定） | Issue 検出・ルーティング判断が主。実装ステップは Sonnet へ切り替える |
| `theme-discovery` | スコアリングフェーズ（frontmatter に設定） | スコア計算・Issue 更新のみ。台本化判断フェーズは Sonnet を維持 |
| `sns-publisher` | 検出フェーズのみ（本文セクションで定義） | 配信対象動画の検出・YAML 読み込みのみ。記事生成フェーズは Sonnet を使用 |

**原則** :
- 迷ったら Sonnet を選ぶ。Opus は明確に必要な場合のみ
- 並列サブエージェントは可能な限り Haiku を使い、コストを抑える
- 品質が不十分な場合はモデルを上げて再実行する（Haiku → Sonnet → Opus）
- 台本生成（Phase 3）では `/effort xhigh` + `/model opus` を推奨。現行 Opus は既定 effort が `high` のため xhigh の明示指定が必要

### effort によるトークン最適化（メインセッション）

**現時点の制約**: Agent tool のパラメータに `effort` は含まれない（`model` / `isolation` / `run_in_background` のみ）。サブエージェントへの effort 直接指定は不可。メインセッションの `/effort` 設定はサブエージェントに引き継がれない。

**メインセッションの `/effort` は 5 段階（`low` / `medium` / `high` / `xhigh` / `max`）。v2.1.105+ で xhigh が追加。現行 Opus（`opus`）のデフォルトは `high`。旧 Opus 4.7 から切り替えると effort が自動的に `high` にリセットされる点に注意。**

**メインセッションの推奨 effort**:

| タスク種別 | 推奨コマンド | 理由 |
|-----------|------------|------|
| 台本生成・設計判断（**`opus`**） | `/effort xhigh`（明示） | 現行 Opus の既定は `high` のため明示指定。コーディング/エージェント/知能重視に最適 |
| 複雑な実装・レビュー対応（Sonnet 5） | `/effort high` | 品質優先で進める場合の基準値 |
| 通常の実装・PR 対応（Sonnet 5） | `/effort medium` | high よりトークンを節約しつつ実用的な品質を維持 |
| 定型チェック・ルーティング判断 | `/effort low` | 高速・最小コスト |

**サブエージェントのコスト最適化（effort 指定の代替手段）**:

| 手段 | 効果 | 実装方法 |
|------|------|---------|
| **モデル選択（最優先）** | 60〜80% 削減 | `model="haiku"` を積極的に使う |
| **プロンプト指示** | 10〜30% 削減 | 「要点のみ・箇条書き・詳細説明不要」を先頭に記載 |
| **出力凝縮の明示** | 20〜40% 削減 | 「1,000〜2,000 トークンのサマリーで返す」と明示 |

Haiku エージェント向けプロンプト先頭テンプレート:

```
# 出力ルール（必ず守ること）
- 箇条書き・要点のみ（詳細説明・前置き・謝辞は省略）
- ファイル全文でなくパスと行番号のみ返す
- 結果は1,000〜2,000トークン以内
```

## サブエージェントの高度な機能

### Verbalized Sampling（重要な出力の並列候補生成・#369 に伴い agent-team-summary.md から移設）

**重要な出力は候補を並列生成してから選ぶ**: タイトル・冒頭フック・設計案など「最初の 1 案がそのまま採用される出力」は、Haiku 3〜5 本で角度の異なる案を同時生成し、選択基準を当てて選ぶ。選択理由を 1 行記録する（1 案直行は Anchoring を招く）。

### ワークツリー隔離（`isolation: "worktree"`）

サブエージェントを一時的な Git ワークツリーで実行し、メインの作業ディレクトリと完全に隔離する。

```
Agent tool 呼び出し例:
  isolation: "worktree"
  prompt: "V008 の画像素材をチェックして..."
```

**活用シナリオ**:
- 画像パイプラインと音声パイプラインを **異なるブランチで並行実行**
- セルフレビューを隔離環境で実行（メインの作業を中断しない）
- 実験的な変更を安全にテスト

**制約**:
- ワークツリー内で変更がなければ自動クリーンアップされる
- 変更があった場合、ワークツリーのパスとブランチ名が結果として返される
- メインのワーキングディレクトリとファイルの競合が発生しない

### バックグラウンドエージェント（`run_in_background: true`）

サブエージェントをバックグラウンドで実行し、完了時に自動通知を受け取る。

**活用シナリオ**:
- ファクトチェックをバックグラウンドで実行しながら台本生成を続行
- AI レビュー依頼後、レビュー到着をバックグラウンドで監視
- theme-discovery のニューススキャンをバックグラウンドで実行

**注意**: バックグラウンドエージェントの進捗をポーリングしない（`sleep` ループも `ReadNotifications`/`TaskGet` の連打も同じ）。待ち方はターンを終えることで、通知は後のターンで届く（§F-8「『待つ』の作法」）。

### 1M コンテキスト活用ガイドライン

Opus / Sonnet の 1M コンテキストウィンドウを効果的に活用するためのガイドライン。

| パターン | 従来（200K） | 1M コンテキスト |
|---------|------------|----------------|
| リサーチ + 台本生成 | リサーチを要約してから台本生成 | リサーチ全文 + キャラ設定 + 既存台本を同時参照可能 |
| レビュー | ファイルごとに分割レビュー | 関連ファイル一括読み込みでコンテキスト横断レビュー |
| パイプライン | 5 ステップごとに手動圧縮 | 10+ ステップでも圧縮なしで続行可能 |

**ただし**:
- 1M あっても不要な情報は渡さない（コスト効率とレイテンシ）
- サブエージェントの出力凝縮ルールは引き続き適用する
- Haiku はコンテキストウィンドウが小さいため、渡す情報を厳選する

## コンテキストコンパクションパターン

長時間実行タスク（Phase 3 台本生成、Phase 4 素材制作など）でコンテキストウィンドウが膨張する問題に対処するため、以下を実践する。

### サブエージェントの出力を凝縮する

- サブエージェントは成果物の全文ではなく **1,000〜2,000 トークンの構造化サマリー** をメインエージェントに返す
- **例外: 台本分割生成**（Phase 3）では、サブエージェントはセクションJSONをそのまま返す（統合のため全文が必要）。ただし1セクション分のみなので肥大化しない
- サマリーのフォーマット例:

```json
{
  "summary": "作業内容の1〜2文での要約",
  "outputs": ["生成したファイルのパス一覧"],
  "key_decisions": ["重要な判断分岐とその理由"],
  "warnings": ["要注意事項（fact_check_flags 件数など）"],
  "next_recommended_action": "次のステップの提案"
}
```

### 長期タスクの検証ポイント設計

エラーは **複合的に蓄積する**（ステップごとの精度 95% × 10 ステップ = 全体成功率約 60%）。
この劣化を防ぐため:

- 5 ステップごと（または Phase 遷移時）に必ず **検証ポイント** を設ける
- 検証は独立したサブエージェント（`model="haiku"`）に委ねて並列化する
- 問題が検出されたら **即座に STOP** してメインエージェントに報告し、続行可否をユーザーに確認する

### パイプライン依存関係（アーキテクチャ制約・プロジェクト例）

> ⚠️ 以下の依存グラフは **出自プロジェクト（動画制作）の実例**。自プロジェクトのパイプライン
> 依存関係に読み替えること（「下流開始前に上流成果物の承認を確認する」原則が本体）。

制作パイプラインには厳密な依存関係がある。下流を開始する前に上流の成果物が「承認済み」であることを確認する。

```
台本JSON（Phase 3）
  └── タイムド台本（Phase 4: voicevox-audio 出力）
        ├── 音声WAV（Phase 4）
        └── 画像素材（Phase 4: image-generator 出力）
              └── Remotionレンダリング（Phase 5）
                    └── YouTube公開（Phase 6）
```

- 上流の成果物が `content/` に存在し、PR がマージ済みであることを確認してから下流を開始する
- Phase をまたぐ作業の開始前に `docs/production-flow.md` の「前提条件」を確認する <!-- refcheck:ignore -->

## プロジェクト固有オブザーバーエージェントのオブザーバーモード

> ⚠️ **このセクションは出自プロジェクトの実例を一般化したテンプレート**。
> 「レビュアーA」= 技術監修役、「レビュアーB」= 初心者目線チェック役という
> 2 役割構成の実運用テンプレートを一般化して残している。
> 自プロジェクトでは `.claude/agents/<name>.md` に定義した自分のレビュー役・監修役に
> 名前・禁止事項・チェック観点を置き換えて使う（テンプレート構造＝参加レベル・JSON 出力・
> ゲート昇格条件は汎用）。

### オブザーバーモードとは

> **オブザーバーエージェント**: 結果がワークフローの続行可否（PASS/FAIL）に影響しない。コメント・感想・追加観察を出力するだけ。メインエージェントがその出力を「参考情報」として扱い、無視しても処理が進む。

対義語は「ゲートエージェント」（FAIL 時に次ステップをブロックする）。オブザーバーは基本ノンブロッキングだが、ブランド毀損・技術的誤りを指摘した場合は自動的にゲートへ昇格する。

### 呼び出し側の責任範囲

- `run_in_background: true` で起動してよい（ブロッキング不要）
- オブザーバーが応答しなかった場合でも処理を続行する
- `critical` または `character_issues` に1件以上の指摘がある場合はゲートとして扱い、メインアシスタントが修正する
- オブザーバー結果は Issue コメントまたは PR 説明に「参考情報」として追記する

### レビュアーA（技術監修役）向け標準呼び出しテンプレート

```
参加レベル: Lv{1/2/3}

# 絶対禁止（自プロジェクトのキャラ設定があればここに口調制限を記載。例: 方言禁止・語尾禁止等）
- 「AIとして」等の自己開示禁止
- 指摘のみ。「修正します」は禁止
- 初心者目線発言禁止（それはレビュアーBの役割）

# タスク
{確認対象ファイルパスまたはテキスト}

# チェック観点
{スキル別の確認項目}

# 出力フォーマット（Lv1/2/3すべてJSON必須。`critical` と `character_issues` は必ず含める）
{"reviewer":"reviewer_a","verdict":"PASS|WARN|FAIL","critical":[],"character_issues":[],"warnings":[],"observations":[],"summary":""}
```

### レビュアーB（初心者目線役）向け標準呼び出しテンプレート

- Read ツールのみ使える。技術的解説禁止
- 「修正します」は禁止

# 出力フォーマット（Lv1/2/3すべてJSON必須。`character_issues` は必ず含める）

### @owner（飼い主プロキシ）向け標準呼び出しテンプレート

> **@owner は飼い主の意思決定パターン・美的センス・世界観・センシティブラインを代弁するオブザーバー兼プロダクトオーナー（PO）。** 2 つの面を持つ: ① コンテンツレビュー時は **予測コメントのみ**（A-1〜A-6 の自動承認はしない・本テンプレートの呼び出しはこの面）/ ② PO としては `sp:*` / `priority:*` ラベルの較正を **実行権限付き** で行う（`mcp__github__issue_write`）。権限境界・tools の正本は `docs/rules/session-sprint-rules.md`（§4 PO ロール）と `.claude/agents/owner.md`（SSOT）。`status:*` 操作・Issue クローズ・A-1〜A-6 自動承認はどちらの面でも禁止。

```
参加レベル: Lv{1/2/3}

# 絶対禁止（@owner 設定）
- A-1〜A-6（既約境界外）の自動承認禁止（予測コメントのみ）
- 飼い主の口調・一人称になりきらない（第三者視点で「飼い主はこう反応しそう」）
- 「AIとして」等の自己開示禁止
- 技術判断（@reviewer_a）・初心者目線（@reviewer_b）の領域に踏み込まない
- 指摘・予測のみ。「修正します」は禁止

# タスク
{確認対象ファイルパスまたはテキスト（台本・SNS投稿・サムネ・メタデータ・企画案）}

# チェック観点
世界観の一貫性・キャラ設定・美的センス・センシティブライン予兆・「飼い主に刺さるか」予測

# 出力フォーマット（Lv1/2/3すべてJSON必須。`sensitive_flags` `worldview_flags` `escalate_to_human` は必ず含める）
{"reviewer":"owner","verdict":"PASS|WARN|FAIL","owner_would_say":"","sensitive_flags":[],"worldview_flags":[],"escalate_to_human":[],"summary":""}
```

- `sensitive_flags` / `worldview_flags` に1件以上 → ゲート扱い（修正必須）
- `escalate_to_human` に1件以上 → メインアシスタントが飼い主本人への確認フローに回す

| refinement | 後段チェック型 | スコア計算後・Issue昇格前 | レビュアーA（Lv2）＋レビュアーB（Lv2・Haiku推奨） | ノンブロッキング（警告追記のみ） |

### @owner 統合の段階導入ポイント（推奨・順次配線）

> ⚠️ **L-094 desync 防止**: 以下は @owner を差し込む **推奨ポイント** であり、各スキルの SKILL.md への実際の配線は段階導入する。配線が完了したら本表の上段（スキル別統合パターン）に正式行として移し、同一 PR で SKILL.md を更新する。「未配線なのに統合済みと書く」ことを禁止する。

| 優先 | スキル | 差し込みタイミング | @owner の役割（代弁する観点） | ブロッキング性 |
|------|-------|-----------------|--------------------------|--------------|
| P1 | sns-organic-pipeline | Step 4 キャラ監修（@reviewer_a/@reviewer_b）と並列 | 公開前のセンシティブ予兆・世界観・「飼い主に刺さるか」（Lv2） | sensitive/worldview flags でゲート昇格 |
| P1 | sns-publisher | 記事ドラフトレビューチームに追加 | 紹介文の世界観・美的トーン（Lv2） | sensitive/worldview flags でゲート昇格 |
| P2 | script-team-reviewer / screenplay-reviewer | 既存チームと並列 | ナラティブ・キャラ設定・世界観のブレ（Lv2〜3） | worldview flags でゲート昇格 |
| P3 | metadata-reviewer | PASS 動画のスポット監査 | タイトル/サムネの「飼い主に刺さるか」（Lv1） | ノンブロッキング |
| P3 | waiting-user-handler | A 区分提示前 | 「飼い主なら GO/NG しそう」の予測を推奨案に添える（Lv1） | ノンブロッキング（本人承認は不可侵） |

**@reviewer_a / @reviewer_b との並列起動順序**: 台本・SNS では `@reviewer_b（初心者）→ @reviewer_a（技術）→ @owner（世界観・美的・センシティブ）` の3者並列でバランスが取れる。役割（観点）が矛盾した場合は優先順位で打ち消し合わせず、各オブザーバーのゲートシグナル（@reviewer_a の技術 `critical`・@reviewer_b の `character_issues`・@owner の `sensitive_flags` / `worldview_flags`）を **いずれも独立した修正必須シグナル** として扱い、どれか 1 つでも立てば修正する。本人承認が要る項目（`escalate_to_human`）は飼い主への確認フローに回す。

## 注意事項

- 依存関係のあるタスクは逐次実行する（調査結果が実装に必要な場合など）
- サブエージェントの結果はメインエージェントが統合し、ユーザーに簡潔に報告する
- 同じ作業をメインエージェントとサブエージェントで重複して実行しない
