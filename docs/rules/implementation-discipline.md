## 1. 層構造・依存方向の判断チェックリスト（スタック非依存）

**大原則: 依存の矢印は常に内側（ドメイン）へ向く。** 内側は外側を知らない。

実装・レビューのときに次の 4 問を順に当てる。**層の数は指定しない** — 最小構成は
「ドメイン / 外部接点」の 2 層でよい。

| # | 問い | 違反のシグナル |
|---|------|--------------|
| **L-1** | この型・関数は **ドメインの言葉** で書けているか | 業務ロジックの中に外部技術の語彙（テーブル名・HTTP ステータス・SDK のクラス名・環境変数名）が漏れている |
| **L-2** | 依存の矢印は **内向き** か | ドメイン側のモジュールが DB クライアント・HTTP クライアント・フレームワークを import している |
| **L-3** | **外部世界との接点**（DB・HTTP・ファイル・時刻・乱数・標準入出力）は境界に隔離されているか | 業務ロジックの途中で `now()` を呼ぶ・ファイルを直接読む。テストのたびに外部を用意しないと動かない |
| **L-4** | 層を 1 つ増やす前に、**より単純な解** から始めているか | 1 箇所しか使わない抽象化レイヤー・実装が 1 つしかないインターフェース（YAGNI・`CLAUDE.md`「やってはいけないこと」） |

**判断が割れたときの記録先**: 下流プロダクトなら `product-brief.md` §5.1 の決定ログへ 1 行。
tsukuru-studio 自身なら Issue コメントか最初のコミットメッセージへ 1 行（`user-confirmation-minimization.md`
§3 item 0 の「仮定を 1 行記録」と同じ扱い）。

> **L-4 は他の 3 問より強い。** L-1〜L-3 を満たすために層を増やすのは、増やす対象が実際に 2 つ以上の
> 実装・2 つ以上の呼び出し元を持つときだけである。「クリーンアーキテクチャだから」を理由に空の層を
> 作らない（`D-12`「空のゲートは無いゲートより悪い」と同型の失敗）。

### 1.1. tsukuru-studio 自身への当てはめ

母艦のコードは `tools/` 直下のフラットなスクリプト群であり、**現時点で層構造を持たない**。
L-1〜L-4 が実際に効くのは、新規に書くコードが **単一ファイルに収まらなくなったとき** である。
それまでは L-3（外部接点の隔離＝テストしやすさ）と L-4（YAGNI）の 2 問だけを当てればよい。

`tools/check_implementation_discipline.py` の `Repo` / `MemoryRepo`（ファイルシステム接点を
1 クラスへ閉じ、self-test はメモリ実装を差し込む）が L-3 の最小適用例である。

## 2. TDD の実行規律（どこまでを必須とするか）

`D-36` の段階適用を、そのまま 3 段の必須ラインへ落とす。

| 段 | 対象 | 規律 |
|---|------|------|
| **Must** | **新規に追加する** 実行可能ユニット（ツール・フック・スクリプト・モジュール） | **同じ PR にテストの裏付けを含める**。裏付けの無い新規追加はゲートがブロックする |
| **Must** | **バグ修正** | **先に失敗するテストを書いてから直す**。再現テストの無い修正はバグ修正として完了扱いにしない |
| **Should** | 既存ファイルの変更（裏付けが無いもの） | その PR の範囲で付けられるなら付ける。付けられないなら Warning のまま進めてよい |
| **Not** | 既存ツール群の一括テスト整備 | 本規律では要求しない。必要なら別 Issue として計画的に消化する（遡及リファクタしない・`D-36`） |

> **なぜ「既存の変更」を Warning に留めるか**: 母艦の `tools/*.py` は現状 56 件中 28 件しか裏付けを
> 持たない（2026-09-13 実測）。触った瞬間に Error にすると、1 行の修正でもテスト新設が必須になり、
> `D-36` が明示的に禁じた遡及リファクタと実質同じ負荷になる。**Warning は「対象外」の意味ではない** —
> 規律は適用され、判断だけが実装者に委ねられる。

### 2.1. 「テストの裏付け」の具体形（本リポジトリの既存規約に乗る）

新しい規約は発明しない。既にハーネスが実行している 2 つの形のどちらかを満たせばよい。

| 対象 | 裏付けの形 |
|---|---|
| `tools/*.py` | ソース内に **`--self-test`** を実装する、または `tools/test_<name>.sh` を置く |
| `.claude/hooks/**/*.sh` ・ `scripts/*.sh` | `tools/test_<name>.sh` を置く（ファイル名のハイフンはアンダースコアへ） |

いずれも PR 前ゲート（`tools/self_review_check.py` の `self_test_errors()` ・
`_companion_test_script_targets()`）が **差分に含まれるものを実際に実行する**。
つまり裏付けの存在は「実行される検証の存在」と一致している。

**照合は厳密一致で行う**（緩めると規律そのものが素通りする。Layer 1 セルフレビューで実証済み）:

- 対応テストは `tools/test_<name>.sh` の **完全一致**。前方一致にすると `tools/pr.py` が
  無関係な `tools/test_pr_confirm_marker.sh` を裏付けと誤認する
- `--self-test` は **引用符付きリテラル**（`"--self-test"` / `'--self-test'`）だけを数える。
  素の部分文字列一致にすると `# TODO: implement --self-test later` のような
  「未実装であることを述べたコメント」や docstring の Usage 行で通過できてしまう

**rename の扱い**: `git mv` で新しいパスへ移して内容も書き換えた変更（git の `R<100`）は
**新規扱い（Error）** にする。base に無いパスへ書き換え済みのコードを置く操作であり、
実質「新規に書くコード」だからである。純粋なリネーム（`R100`）は新規のコードが 1 行も
増えていないので **既存扱い（Warning）** に留める。

### 2.2. Red → Green の順序について

順序（テストを先に書いたか）は **機械では判定できない**。判定できるのは「同じ PR にテストがあるか」
までである。したがって順序は規律として書くが、ゲートでは強制しない — ただし **バグ修正の再現テスト
だけは順序が成果物に現れる**（先に書けば必ず 1 度失敗するので、その失敗を Issue か PR に 1 行残せる）。

## 3. 機械検査の範囲（何が機械化され、何が判断に残るか）

| 規律 | 機械検査 | 残る判断 |
|---|---|---|
| §1 層構造・依存方向 | **無し（意図的）** | 全部（L-1〜L-4 は人・AI が当てる） |
| §2 テストの裏付け | `tools/check_implementation_discipline.py` | テストの中身が意味のある検証か・Red → Green の順序 |

**§1 を機械化しない理由**（`D-12` の裏返し）:

- tsukuru-studio 自身は層構造を持たないフラットなスクリプト群であり、層検査を置いても
  **検査対象が 0 件の「空のゲート」** になる。空のゲートは無いゲートより悪い（`D-12`）
- 下流プロダクトは技術スタックが `C-4` で初めて決まるため、母艦側に静的解析を常設できない。
  実体が要るのは生成されたプロダクト側であり、それは `M-3` 射程（`prd.md` §3.2 の「やらないこと」）

**fail-closed（`D-12`）**: `check_implementation_discipline.py` は、登録ルール（`RULES`）が 0 件のとき、
および `--self-test` のケースが 0 件のときに **exit 2** で失敗する。ゲートが存在するのに何も検査して
いない状態を成功終了させない。ルールを一時的に外すときは、**なぜ外すかを本節へ書いてから外す**。

**配線**: `tools/self_review_check.py`（`pre-pr-create-check.sh` が PR 作成前に自動実行）から呼ばれる。
Error は PR 作成をブロックし、Warning は報告のみ。単体では次のとおり実行できる。

```bash
python3 tools/check_implementation_discipline.py --changed     # 変更ファイルを検査
python3 tools/check_implementation_discipline.py --self-test   # 自己テスト
```

### 3.1. 逃げ道（`SELF_REVIEW_DISCIPLINE=warn`）

`SELF_REVIEW_DISCIPLINE=warn` を付けると Error を Warning へ降格し、PR 作成をブロックしない
（`SELF_REVIEW_SECURITY` / `SELF_REVIEW_SELFTEST` と同じ既存パターン）。**降格しても違反自体は
必ず報告される**（沈黙しない）。

用途は 1 つに限る: **`M-1` の唯一の KPI（上流工程の動線実証）に直結するタスクが本ゲートで
止まったとき**。`D-36` は `M-1` の完了条件を押しのけないことを前提に置いた決定であり、
その前提を守るための明示的な回避路である。使ったことは差分に残らないので、**使ったら
対象 Issue へ 1 行記録する**（何を回避し、テストをいつ足すか）。

> `M-1` との関係を隠さない: 本規律は `M-1` に着手可能な Issue が 1 件も無い発火で
> `M-2` 射程の #84 を消化して整備された（`docs/routines.md` §2.2 の段階解禁）。
> `roadmap.md` / `project-mission.md` が `M-1` でやらないとした「`run_checks.sh` /
> `architecture-rules.md` / ID 体系の **フル移植**」は引き続き行っていないが、
> 本ゲートが `M-1` の作業を止めうる点は実在するリスクなので、上記の逃げ道で受ける。

### 3.2. 既知の限界（隠さない）

- テストの **中身** は見ない。`exit 0` だけのテストでも通る
- 完全一致にしたため、`scripts/bootstrap.sh` のように別名のテスト
  （`tools/test_bootstrap_marketplace_guard.sh`）しか持たないファイルは「裏付け無し」と
  報告される。既存ファイルなので Warning 止まりであり、綴りを規約へ揃えるか裏付けを足すかは
  実装者が判断する
- 新規／既存の判定は git の name-status（`A` / `M` / `R<score>`）に依存する。スコアを伴わない
  `R` / `C` は安全側（新規扱い）へ倒す。git が使えない環境では `--paths` / `--new` の明示指定に退行する
- PR 前ゲートの共有実行時間予算（`GATE_STARTED` 起点・60 秒）を超えていたら **実行せず Warning** を
  返す。ここでブロックすると外側 timeout の `exit=124` と同じ「チェッカー自体の異常で PR 作成が
  通る」経路を自分で作ることになるため

## 4. 完了・成功の定義

- [ ] 新規に追加した実行可能ユニットに、`§2.1` のいずれかの裏付けが同じ PR に入っている

- [ ] 層を増やした場合、L-4（YAGNI）を通過している（2 つ以上の実装か呼び出し元がある）
- [ ] 下流プロダクトで既定（Clean Architecture / DDD / TDD）を外した場合、`product-brief.md` §5.0 / §5.1 の
      決定ログに理由が 1 行残っている
- [ ] `python3 tools/check_implementation_discipline.py --self-test` が成功する
