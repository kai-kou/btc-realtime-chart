## §3 item 8 補完: 論点が複数あって互いに依存するときの出し方（フロンティア方式）

Hot 版 §3 item 8 の書式要件（**選択肢は最大 2 つ・各選択肢に判断材料 1 行・推奨を明示**）は
**1 問を出すときの形** を決めている。本節が補うのは、**問いが複数あって互いに依存しているとき、
どれをいつ出すか**という別の軸である（1 問あたりの形は本節でも一切変えない）。

### 設計ツリーとフロンティア

決定は木になる。ある決定が決まって初めて意味を持つ決定が、その下にぶら下がる。
**フロンティア** は「前提がすでに片付いていて、**今** 答えられる決定」の集合。

- **フロンティアは 1 ラウンドでまとめて出す**。1 問ずつ往復すると、独立な問いの数だけユーザーを待たせる
- **他の問いの答えに依存する問いは、そのラウンドに混ぜない**。答えを仮定して立てた問いは、
  仮定が外れた瞬間に無駄になる（ユーザーの回答も無駄になる）
- 回答が返るたびにフロンティアを **引き直す**。片付いた決定がその下の決定を解放する
- **フロンティアが空になったら終わり**。木のどの枝も、黙って仮定されたまま残っていない状態

### 事実は自分で埋める

フロンティアに並べる前に、**環境から答えが取れるもの** は問いから除く。原則の本文は
`problem-investigation-protocol.md` Step 2 の「事実調査は Claude の仕事、決定だけがユーザーのもの」
に置いてある（ここでは繰り返さない）。フロンティアに固有なのは **時間差の扱い** だけである:
調査に時間がかかっても止まらず、走らせたまま **その結果に依存しない問いを先に出す**
（依存する問いだけが結果を待つ）。

### 1 ラウンドの形

各問いは Hot 版 §3 item 8 の書式（選択肢 2 つ・判断材料 1 行・推奨明示）をそのまま守る。
`AskUserQuestion` を使う場合も同じ。**フロンティアは問いの出す順を決めるだけで、問いの形は変えない。**

> ⚠️ これは A-1〜A-6 の境界を広げる規定では **ない**。そもそも確認してよい論点（境界外）が
> 複数あって依存し合っているときの捌き方であって、確認してよい論点の範囲は Hot 版 §1 のまま。

## §6. D カテゴリ（外部要因）の自律最小化ルール（プロジェクト例）

外部課金・BAN・プラットフォーム制約は設定変更（A-6）のみユーザー作業だが、**影響を自律的に最小化** する。

⚠️ 下表は **プロジェクト例**。各プロジェクトが利用する外部 API・プラットフォームに読み替える（汎用ベースに存在しないツール名を含む）。

| 外部要因（プロジェクト例） | 自律最小化策 | ステータス |
|---------|------------|-----------|
| 画像生成 API の請求ハード上限 | 枯渇前に Slack 予告。**実測検知時は `tools/api_depletion_alert.py` がハード上限到達を検知した瞬間に Slack 即通知（A-6）**。枯渇後は代替 provider の HTTP フォールバックで継続。代替エンジン降格は品質一貫性への影響評価が必要なため実装 Issue で慎重に検討 | 予告 + 実測即時通知 <!-- refcheck:ignore --> |
| 外部 API クレジット枯渇 | 予算トラッカーで枯渇前に予告（予測型）。**実測検知時は `tools/api_depletion_alert.py` が投稿/取得スクリプトのエラーパスでクレジット枯渇を検知した瞬間に Slack 即通知（A-6。推定残高が健全表示でも取りこぼさない）**。月初リセットを監視し復旧を自動確認 | 予告 + 実測即時通知 <!-- refcheck:ignore --> |
| GitHub Actions 課金超過 | Path フィルタで不要 CI を削減 + Lv3 フックで CI 前チェックを吸収し実行頻度を下げる | 実行頻度の継続的削減（プロジェクトで追跡） |

「枯渇したので止めます」で終わらせず、**フォールバック経路で可能な限り処理を継続** することが D カテゴリの自律運用の要件。

### A-6 のうち「ダッシュボード遷移型」への備え（未発生・参照実装のみ）

上表の A-6 は 2 件とも **枯渇の予告とフォールバック継続** で完結する型で、ユーザー側の作業は
設定画面での 1 操作に閉じている。一方 Hot 版 §1 の A-6 定義行は **OAuth トークン再発行 /
コンソールの API 有効化** も名指ししており、こちらは「複数の画面を順に開き、各所で値をコピーし、
`.env` や CI シークレットに書き戻す」という **手順そのものが長い** 型になる。

**この型は本リポジトリでまだ一度も発生していない**（`git log` を課金・OAuth・アカウント設定で
grep して 0 件）。したがって今は **スキルを作らない**（実需要が無いまま在庫を積むのは YAGNI であり、
スキルを 1 本増やすと description が毎ターン常駐する — その常駐コストは現状 `check_hot_budget.py` の
集計に入っておらず「ゼロ」ではなく「未計測」である）。失うと惜しい設計知見だけをここに残す。

**参照実装**: mattpocock/skills `engineering/wizard`（MIT）。人間しかできない手順を**対話 bash
スクリプト**に落とす。ライブラリ部（進捗表示・確認ゲート・URL オープン・秘密値の非表示入力・
`.env` への冪等 upsert・CI シークレット書き込み・完了サマリー）は共通テンプレートが提供し、
著者は **ステージ定義だけ** を書く。設計上の要点:

- 値を尋ねる **前に** その値がある URL を開く（人間が探さずに済む）
- 1 ステージ = 1 つの用件に絞る（画面をクリアするので、必要な情報がスクロールで消えない）
- 秘密値は非表示入力、書き込み先（`.env` / CI シークレット / 両方 / どこでもない）をステージごとに確定
- 不可逆な操作の前に必ず確認を挟む
- 既定は使い捨て。繰り返し使うセットアップ手順になったときだけリポジトリに置く

**昇格の発火条件**: 🔴 **ダッシュボード遷移を伴う A-6 が実際に初めて発生した時点で**、この参照実装を
もとに `.claude/skills/wizard/` の新設を検討する。それまでは、現行どおり
`user-notification-triage.md` §3 の「具体的ユーザーアクションを 1 文で」に従ってテキストで案内する。
