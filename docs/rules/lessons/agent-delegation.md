# Warm 層 教訓 — サブエージェント委譲・Agent Teams（agent-delegation）

サブエージェント / Agent Teams への委譲で「回答が空になる」「期待しない形式で返る」類の教訓を蓄積する。
タスク依存で必要時に Read する（常駐しない）。常駐サマリーは `agent-team-summary.md`、
仕様表の SSOT は `agent-team.md` §「委譲が『空回答・期待外の回答』になる公式要因」。

---

## L-121: 委譲先が「空回答・期待外の回答」を返すのはハーネス仕様が原因のことが多い（2026-07-29）

**パターン**: サブエージェント / Agent Teams に委譲したのに、返り値が空・極端に短い・英語・
プロジェクト規約を無視した形式で返る。「モデルが怠けた」と解釈して再委譲やプロンプト強化を繰り返すが直らない。

**根本原因（3 層）**:

- **直接原因**: 委譲先に届く前提（ツールプール・コンテキスト・システムプロンプト）が、委譲側の想定と違う。
- **中間原因**: Claude Code の仕様がそれを **エラーなしで** 起こす。
  ① `tools` に書いたツールが 2 段フィルタで **silent に削除** され、全滅すると zero tools（= 空回答）。
  v2.1.198 以降 **background が既定** のため、background 許可リスト外の組み込みツールは常に消える。
  ② `Explore` / `Plan` は **CLAUDE.md を読まない**（公式仕様・変更不可）。
  ③ **output style はサブエージェントに継承されない**（fork を除く）。`concise-neko` の日本語・ねこ規律は届かない。
  ④ API 打ち切り時、**foreground** で出力がツール呼び出しだけだと `Agent terminated early due to an API error`
  （v2.1.199 では **空の partial result**）。**background**（既定）では failed とマークされ、
  終了メッセージにエラー名と最後の出力が含まれる。
- **根本原因**: 「CLAUDE.md とルールに書けば委譲先も従う」という誤った前提でチーム設計をしていた。
  委譲先は **別のシステムプロンプト・別のコンテキスト・別のツールプール** で動く独立実行環境である。

**対策（実装済み）**:

- `agent-team.md` に公式フィルタ表と全制約を F-1〜F-7 として明文化（SSOT）。常駐サマリーを `agent-team-summary.md` に追加。
- `tools/check_agent_definitions.py` が `.claude/agents/*.md` の `tools` を公式フィルタと突合し、
  zero tools（空回答）になる定義を検出する。`tools/self_review_check.py` が `.claude/agents/` 変更時に自動実行する。

**禁止パターン / 推奨パターン**:

```
❌ 「CLAUDE.md に日本語で返すと書いてあるから Explore も従うはず」
✅ Explore / Plan への委譲プロンプトに、必要なルール（言語・形式・除外パス）を毎回再掲する

❌ 空回答を見て「サブエージェントが怠けた」と判断し同じプロンプトで再委譲する
✅ ① tools が全滅していないか（check_agent_definitions.py）② API 打ち切りでないか の順に切り分ける

❌ サイレント規律（L-111）を委譲プロンプトにもそのまま適用する
✅ 「最終テキストは親への返り値。結論・根拠・該当箇所を必ず含める」と明示する（返り値は実況ではない）
```

## L-122: フックが公式スキーマに無いフィールドを読むと、静かに壊れて「偽の観測」を注入する（2026-07-29）

**パターン**: `subagent-stop.sh` が SubagentStop の入力を `is_error` / `result` として読んでいたが、
公式スキーマにこの 2 つは存在しない（正しくは `stop_reason` / `last_assistant_message`）。
`jq` も `.get()` も既定値を返すだけでエラーにならないため、フックは壊れたまま動き続けた。
結果、サブエージェントの異常終了時に **最終出力が常に空の異常報告** をオーケストレータへ注入していた
（`最終出力（末尾）:` の直後が空行）。診断できないうえ、成果が失われたかのような誤った観測になる。

**根本原因（3 層）**:

- **直接原因**: 非実在フィールドを読み、既定値（`false` / `""`）を実データとして扱った。
- **中間原因**: フック入力のフィールド名を公式ドキュメントの **JSON 例（逐語）** と突き合わせず、
  要約・記憶で書いた。フック出力は Claude の観測になるため、誤りが「事実」として下流へ流れる。
- **根本原因**: フックの入力契約に対する機械的・手続き的な検証手段が無く、壊れても誰も気づかない。

**対策（実装済み）**:

- `hook-events-reference.md` §4.5 に「フック入力 JSON のフィールド名は公式スキーマで検証する」と
  Stop / SubagentStop の逐語スキーマを明記。
- `subagent-stop.sh` を `stop_reason` / `last_assistant_message` へ修正し、判定を **fail-safe に反転**
  （既知の異常語を含むときだけ発話し、空・未知の `stop_reason` は無音）。

**禁止パターン / 推奨パターン**:

```
❌ フックの入力フィールド名を記憶や要約から書く（要約経路はフィールド名を取り違える）
✅ 公式 hooks ドキュメントの JSON 例を逐語で確認してから書く（L-113 の姉妹則）

❌ 判定不能なときに「異常」と報告する（Claude の観測を偽情報で汚す）
✅ 異常と断定できるシグナルがあるときだけ発話し、未知・空は無音にする（fail-safe）
```

## L-132: サブエージェント完了を「待つ」つもりで通知確認ツールを連打する（2026-09-13）

**パターン**: 複数のサブエージェント（議論型レビューの参加者等）へ委譲したあと、完了通知が届くまで
`ReadNotifications` を呼ぶ → 「完了待機中」と 1 行出す → また `ReadNotifications`、を十数回繰り返す。
`sleep` は使っていないため「`sleep` ポーリング禁止」ルールには抵触せず、規律違反と自覚しにくい。

**根本原因（3 層）**:

- **直接原因**: 「完了通知を待つ」の *待つ* を「同一ターン内で確認し続ける」と解釈した。
- **中間原因**: ルール側の禁止表現が **`sleep` という手段名に縛られていた**（`agent-team-summary.md` /
  `agent-team.md` / `discussion-review` SKILL.md すべてが「`sleep` ポーリング禁止」とだけ書いていた）。
  手段が変われば同じ浪費が素通りする書き方だった。
- **根本原因**: 「待ち方（= そのターンを終える）」という **正の作法** がどこにも明記されておらず、
  禁止の裏返しをモデルの解釈に委ねていた。

**対策（実装済み・#648）**:

- `agent-team.md` §F-8 に「『待つ』の作法 — 手段を問わずポーリング禁止」を追加（SSOT）。
- `agent-team-summary.md`（Hot 層）・`claude-code-optimization.md`・`discussion-review` SKILL.md の
  「`sleep` ポーリング禁止」を手段非依存の表現に改訂。
- `output-verbosity-rules.md` §2 に「完了待ちの実況」を禁止例として追加（L-111 の待機文脈での再発形）。

**禁止パターン / 推奨パターン**:

```
❌ ReadNotifications →「完了待機中」→ ReadNotifications → …（空振りの繰り返し）
✅ 委譲後は残りの独立作業を進め、無ければターンを終える（通知は後のターンで届く）

❌ 待機中のタイムアウトが怖いので確認出力を挟む
✅ サブエージェント通知はハーネス内イベント。外部イベント待ち（subscribe_pr_activity）の
   ハートビートとは別物で、待機ターンを埋める出力は不要

✅ 例外は無応答判定（目安 10 分）に達したときの SendMessage による生存確認 1 回のみ
```
