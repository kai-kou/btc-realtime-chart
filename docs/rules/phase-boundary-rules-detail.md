## 1. なぜ必要か（正面衝突の明文化・背景全文）

tsukuru は「まだ何を作るか決まっていない段階」（C-1〜C-4: 要件定義・ドキュメント選定・技術スタック選定）を引き受ける。この工程は本質的に **ユーザーとの対話で決定を詰める** ものであり、選択肢を提示して選んでもらうことそのものが仕事である。

一方で、継承元の `kai-kou/claude-code-repository-base` は `CP-6`（ユーザー介入最小化）と `sprint-development-rules.md` の `SD-3`（曖昧点を残さない・確認の発火ラインは「仕様解釈が 2 通り以上あり選択で成果物が変わるとき」に限定）を持ち、**「定義済みルールの範囲では『〇〇してよいですか』を禁止する」** という自律運転を前提にしている。

この 2 つを字面どおり両方とも適用すると、次のどちらかに壊れる:

- **要件定義工程まで `CP-6`/`SD-3` を厳格適用する** → C-1〜C-4 が「最も単純な合理的解釈で仮定を立てて自律実行」されてしまい、ユーザーが本来決めるべきこと（何を作るか・どの技術を使うか）を Claude が黙って決めてしまう。C-3「ユーザーと詰める」が機能しない
- **実装工程まで要件定義並みに質問し続ける** → `SD-3` の発火ライン（仕様解釈の分岐のみ）を超えて日常的に確認するようになり、`CP-6` が意味を失う（Human-in-the-loop アンチパターン化）

明文化しないと「聞いてくるが待たない」（対話のふりをして実際には確認を待たずに進める）、あるいは「実装中も逐一伺いを立てる」のどちらかに倒れる。**フェーズ変数はこの正面衝突を、モデルの裁量ではなく機械判定可能な条件に落とすためのものである。**

> ⚠️ **既知の依存関係（正直に明記する）**: Hot 版は実装フェーズの発火ラインとして `sprint-development-rules.md` の `SD-3` を参照するが、**このファイルは本リポジトリ（tsukuru-studio）にまだ移植されていない**（2026-09-01 時点。`docs/rules/` 配下に実体なし）。移植は `lead_verdict` の `port_boundary.rewrite` に明示リストされていない未確定事項であり、M-2 以降に判断される可能性がある。それまでの間、実装フェーズの発火ラインは Hot 版の記述（`SD-3` の要旨を直接書き下したもの）を正とし、`sprint-development-rules.md` が実在するようになった時点でそちらの記述を正本として参照し直す。**この参照ズレを埋める作業を先回りしない**（担当スコープ外への書き込み禁止）。

## 2. 🔴 A-1〜A-6 を変更しない理由（実測根拠の詳説）

Hot 版が「不変の境界」とだけ書く判断の、実測根拠を以下に残す（`lead_consensus` `A-5` / `scope-skeptic` `F-2`）。

- `tools/triage_notification.py` は `mention = (action_class == "A")` という機械トリアージで、A 区分以外の `@mention` を決定論的に抑制する設計になっている
- A 区分は「最小化すべき例外」であることが通知の信号価値の前提であり、フェーズを理由に A を日常化させると `user-notification-triage.md` §6 の完了条件「真の要対応ゼロの日は `@mention` しない」が恒常的に破れ、通知が意味を失う
- したがって要件定義フェーズの質問は **`@mention` 通知ではなく `AskUserQuestion` による対話** として扱う。両者は別の経路であり、要件定義フェーズで質問が増えても A 区分の `@mention` 発火数が増えるわけではない

C-5（自律運転に入れる状態を作る＝設定一式の生成 + ユーザー操作案内）・C-6（入った後に回す＝ルーティンでの実装・デプロイ・リリース）でユーザー操作が物理的に必要な場面（アカウント設定・可視性変更等）は、フェーズに関わらず引き続き **A-6** として扱う（格上げしない）。

## 3. 要件定義フェーズの質問の作法（詳細）

要件定義フェーズで「多く聞いてよい」からといって、思いつくたびに 1 問ずつ確認しない。

- **1 ラウンドにつき frontier をまとめて聞く**: そのラウンドで解ける曖昧点を洗い出し、まとめて `AskUserQuestion` に提示する。曖昧点 1 つで手を止めて何往復もしない。🔴 **定義（frontier とは何か）・終了条件（frontier が空になること）・「ラウンド数の上限ではない」は Hot 版 `phase-boundary-rules.md` を正とする**（ここで独自の言い回しを保持しない。旧版の「1 ラウンドで」という表現が「ヒアリングは 1 回だけ」と誤読され、実装が固定項目を 1 回聞いて終わる設計に退化した実例がある・`D-33`）
- **各問いに推奨案を添える**: `user-confirmation-minimization.md` §3 item 8 の書式要件（選択肢は最大 2 つ・各 1 行の判断材料・推奨を明示）に従う
- **決定はユーザーのもの**: C-1〜C-4 は Claude が代わりに決めて事後報告する工程ではない。合意（ユーザーの回答）を得るまで、その決定に依存する後続作業には着手しない
- 決定が出たら要件ドキュメント（`docs/framework-templates/product-brief.md` をコピーして埋めたもの等）と、技術選定であれば決定ログへ反映し、Issue コメントに要点を残す

## 4. フェーズ逆流の検知（実装フェーズ中に要件判断が湧いたとき・設計詳細）

実装フェーズ中に「製品として何を作るかそのもの」に関わる判断（要件の再定義・スコープの拡張・技術選定のやり直し等）が湧いた場合、それは Hot 版「実装フェーズの発火ライン」の「仕様解釈の分岐」でも A-1〜A-6 のどれにも該当せず、確認の網を素通りしてしまう可能性がある。

**対策（機械的に置けるゲートのみ）**: 要件ドキュメント（`product-brief.md` の写し等）に **新しい要件 ID を追加する差分を含む PR** には、対応する決定ログエントリ（何を・なぜ変えたか）が無ければ通さないというゲートを置く。実装は `tools/check_phase_reversal_gate.py`（`self_review_check.py` の `phase_reversal_gate_violation()` から呼ばれ、PR 作成前チェックでブロックする）。判定ロジックは `--self-test` で変異テスト（決定ログの追加行だけを取り除いた差分が実際に違反検知されることを実測）を含めて検証できる。

**「新しい要件 ID」の判定基準（Issue #61）**: 追加行に現れた ID ではなく、**変更前スナップショット（差分の pre-image）に存在しない ID** を新規とみなす。pre-image は `git show {base_ref}:{path}` の全文（`base_ref` の既定は `merge-base(origin/{default}, HEAD)`。リネーム時は旧パスも引く）と、差分の削除行から集める。追加行だけを見ると、要件ドキュメントの本文で既存 ID を参照しただけの差分が常に違反として報告され、正当な差分がブロックされる（実測: PR #60）。

2 つの落とし穴があり、どちらも実測で踏んだ。**`base_ref` に `HEAD` を使ってはならない** — ブランチ上でコミット済みの新規 ID が「変更前から存在した」と判定され、ゲートが素通りする。**差分のコンテキスト行を pre-image に使ってはならない** — `self_review_check.py` は `origin/{default}...HEAD`・`--cached`・作業ツリーの 3 経路の差分を連結して渡すため経路ごとに pre-image が違い、作業ツリー差分のコンテキスト行に現れる「コミット済みの新規 ID」を既存扱いして真の違反を見逃す。

### 既知の限界（隠さない）

このゲートは **形式的な差分**（要件 ID が増えている・減っている）でしか発火しない。次のケースは捕捉できない:

- 実装フェーズ中に「これくらいは軽微な仕様解釈だ」と過小評価し、要件 ID を追加せずに実装だけを進めてしまうケース（差分に要件 ID の変化が出ないため、機械ゲートは沈黙する）
- 既存の要件 ID の **意味を変えずに実装だけをこっそり変える** ケース（ID の追加・削除が無いため同上）
- pre-image に「まだ定義されていない ID」への言及（`TODO: FR-2 を足す` 等）が既にあるケース（ID 表記だけを手がかりにする以上、言及と定義は区別できず、その ID の実際の追加を新規と見なせない）
- `base_ref` を解決できない環境（git が無い・`origin` が無い）では pre-image が差分の削除行だけに退行し、上記の偽陽性が再び起こりうる（検知側に倒す安全側の退行であり、沈黙はしない）

これらを機械的に解決する方法は現時点で無い。唯一の補完策は **Layer 1 セルフレビューの観点として「実装が要件ドキュメントの記述と一致しているか」を見る** ことであり、これは人間（レビュアー）相当の判断に依存する。本ファイルはこの限界を機構で埋めた体で記述しない。

## 5. ハーネスとの相性（質問の前にコミット & push する・詳細）

要件定義フェーズで「質問して回答を待つ」とき、次の既存ハーネス挙動と噛み合わない可能性がある:

- Stop フックが未コミット変更のコミットを迫る（`session-safety-rules.md` の WIP 自動コミット）
- `orchestrator-directive.sh`（高コストモデル時のチーム組成指示）が委譲を促す

**回避策**: 質問を投げる前に必ず `session-safety-rules.md`「ユーザー確認前の基本手順」を実行する。

```bash
git status
git add .
git commit -m "[wip] ユーザー確認待ち（{概要}）"
git push -u origin {ブランチ名}
# push 完了後にユーザーへの確認メッセージ（AskUserQuestion 等）を送る
```

これにより、回答待ちの間にセッションが中断・圧縮されても作業内容が失われない。
