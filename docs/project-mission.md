## ミッションステートメント

tsukuru は、`kai-kou/claude-code-repository-base`（汎用 Claude Code 自律運用ベース）が持たない
**「まだ何を作るか決まっていない段階」を引き受け**、白紙のアイデアを対話で要件へ落とし、技術スタック・
インフラを選び、実装からリリースまでを自律運転へ橋渡しする、**サービス・ツール作成に特化した下流レイヤー**
である。

## 解く課題

`claude-code-repository-base` は「決まったプロダクトを自律的に開発・運用する」ための基盤
（PR 自律化・スプリント運用・品質ゲート・マルチセッション競合防止 等）を持つが、**「そもそも何を作るか」
を決める上流工程がフレームワーク化されていない** という具体的な欠落がある。この欠落があるままだと、
新規プロダクトはいずれも「白紙の 1 行」から要件定義を都度アドホックに進めることになり、下流にあるはずの
自律運転の恩恵（PR 自律化・スプリント運用）に接続する前段で毎回ゼロから作業することになる。

tsukuru はこの欠落を埋めるレイヤーであり、以下の工程（`C-1`〜`C-4`。`C-1.5` を含む）を対話とドキュメントで一貫させる:

- **C-1** 要件定義をエージェントとの対話でまとめる（白紙 1 行 → 要件ドキュメント 1 本）
- **C-1.5** 要件を確定する前にリサーチする（設問を 3〜5 本立てて調べ、結果を要件の採否理由・決定ログの理由・未決事項へ接続する）
- **C-2** 必要なドキュメントを選定する（既定は最小 1 本。増やすのはユーザーが要求したときだけ）
- **C-3** ユーザーと詰める（要件定義フェーズに限って質問を許すフェーズ変数。詳細は `CLAUDE.md`「フェーズ変数」節）
- **C-4** 技術スタック・インフラを選定し、二層（決定ログ = 床 / ADR = 天井）で根拠を残す

続く 2 工程は上流工程の出口から先を担う（定義だけ本節に置き、射程は下記のとおり `M-1` の外である）:

- **C-5** 下流プロダクトが **自律運転に入れる状態を作る**（自律運転設定一式の生成 + その適用に要するユーザー操作の案内）
- **C-6** 下流プロダクトが自律運転に **入った後に回す**（ルーティンでの実装・デプロイ・リリース）

`C-5`・`C-6` は下流フェーズ（`M-2` / `M-3`）の射程であり、現マイルストーン（`M-1`）には含めない。
**`C-6` は `M-3` の射程のまま動かさない**（上流工程が通ってドキュメントが出ないと、ルーティン開発支援の設計を
決める材料が揃わないため）。

🔴 **工程 ID は `C-1`〜`C-6`（`C-1.5` を含む）から増やさない。** オーナーの完成像ステップ 8（ルーティンで
リファインメント・スプリント開発が進むよう設定を追加し、ユーザーに手動調整してもらう）は **`C-5` が吸収する**
工程であり、`C-4.5` は新設しない（判断・根拠・却下した代替案の正本は
[`02_requirements/open-questions.md`](./02_requirements/open-questions.md) `D-38`）。

| # | 射程 | 中身 | 代表 Issue |
|---|------|------|-----------|
| 1 | **上流工程の動線**（`C-1`〜`C-4` + リサーチ導線 `C-1.5`） | 白紙 1 行から要件ドキュメント 1 本 + `sp:N` 付き Issue 1 件までを 1 本のスキルで通す | #5 / #57 |
| 2 | **親子同期の土台修理** | プレースホルダ置換欠陥の修正（親への還流はオーナー判断で対応不要・2026-09-23）・子固有資産の台帳・`apply-base` 後の自己検査・ドリフト検知 | #1〜#4 |
| 3 | **配布経路の構築**（publish-sync） | 母艦（`tsukuru-studio`）から配布物（`kai-kou/tsukuru`）へスナップショット公開できる状態にする | #59 |

3 本目が `M-1` に入る理由は、下記「ドッグフーディングの循環」の入口が配布経路だからである（揃った資産が配布
されないと、オーナーが利用者として使う段階に入れず、フィードバックが母艦へ戻ってこない）。配布物の **可視性を
public へ切り替える操作そのもの** は `A-6`（`M-2` 射程）であり、本射程には含めない。

## ドッグフーディングの循環

tsukuru は「作って終わり」のテンプレートではなく、**母艦で整備したものをオーナー自身が利用者として使い、その
不満を母艦へ戻す** 循環で育てる（オーナーの明示決定）。

```
母艦（tsukuru-studio）で整備   →   配布物（kai-kou/tsukuru）へ公開
        ↑                                      ↓
  Issue として母艦へ戻す   ←   オーナーが利用者として使う（ドッグフーディング）
```

- **循環の起点は受け渡し**（`D-41`）: Claude が通しリハーサルを 1 周完走させ、「一連の流れが確立されているはず」と言える状態になったら、オーナーが公開テンプレートリポジトリで実プロダクトを作り始める。それより前の検証は Claude がリハーサルで担う
- **循環の入口は配布経路**（上記 `M-1` 射程 3）。ここが開くまで、この循環は 1 周もしない
- **戻し先は母艦の Issue**（配布物側で直接直さない）。配布物は母艦のスナップショットであり、そちらへ直接コミット
  すると次回の公開で失われる
- 循環が回り始めた後も、**判定に使う指標は下記 KPI の単一指標のまま** である（フィードバック件数・周回数を
  指標に足さない・gaming 防止）

## KPI / 成功指標

議論で確定した単一指標を採用する（複数指標の合成スコアにしない）。指標の中身は 2026-09-23 に `D-41`（本リポジトリの完成＝受け渡し可能な状態）で差し替えた。旧指標（実プロダクト 1 本の完走）は、受け渡し後のオーナーのドッグフーディングへ移した（題材の条件は `Q-1`）。

| 指標 | 目標 | 計測方法 |
|------|------|---------|
| 受け渡し可能な状態への到達（単一の合否判定・`D-41`） | 2026-12-01 時点で、公開リポジトリ `kai-kou/tsukuru` をテンプレートとして作った使い捨てリポジトリで、「〇〇を作って」の 1 行からサンプルアプリのデプロイまでの通しリハーサルが 1 周完走している（上流工程 `C-1`〜`C-4` → 自律運転の設定 `C-5` → 実装・デプロイ `C-6`。デプロイ先は Cloudflare） | リハーサル用リポジトリで ① 要件ドキュメントと `sp:N` 付き Issue が実在すること、② `SP-1` の実装 PR が `state=MERGED` であること、③ デプロイ済み URL（Cloudflare）が応答することを実結果で確認する。リハーサル用リポジトリがテンプレートから作られたことを着手時の Issue コメントに記録する |

**この指標だけが判定に使われる。以下は判定に使わない**（gaming 防止・議論での明示合意）:

- スキル数・ルール行数の多寡
- Issue / PR の消化数（velocity・done_sp）
- 監査プロトコルのスコア
- 対象プロダクトを作る **動機・意図の自己申告**（「実際に使うつもりだった」等の観測不能な内心を合否述語にしない。適格性は `Q-1` の観測可能な 3 条件だけで判定する・`D-31`）

## ミッションに基づく判断基準

| 判断場面 | ミッション指向の選択 |
|---------|-------------------|
| 新機能を今 `M-1` に足すか、後回しにするか | 上記「`M-1` の射程（3 本立て）」のどれにも直結しないなら後回しにし、別 Issue で起票する |
| 汎用化と個別最適化のどちらを取るか | 想定利用者は第三者を含む（ユーザー決定）。ただし汎用化コストが動線 1 本を通す速度を落とすなら、まず 1 本通してから汎用化する（`upstream_design` の「動線 1 本」原則） |
| ドキュメント・ID 体系をどこまで作り込むか | 意味論クラス（`D-n`/`AC-n`/`US-n`/`E-n`/`SP-n`/`M-n` の種類と正本責務分離の規律）だけを汎用資産にし、具体プレフィックスとセクション構成は各プロダクトに委ねる |
| 実装モデル（層構造・設計手法・テストの進め方）をどう決めるか | **クリーンアーキテクチャ** ・ **DDD** ・ **TDD** を既定として採る。下流プロダクトでも tsukuru-studio 自身のコードでも同じ既定を使い、外すときだけ決定ログへ理由を残す（正本は [`02_requirements/open-questions.md`](./02_requirements/open-questions.md) `D-36`） |
| 親ベースとの同期をどう扱うか | ドリフト（ルール差分の放置）と台帳消失（`modules.yaml` の子固有エントリが同期で消えること）を「起きたら直す」ではなく「起きないように機械検知する」ことを優先する |

## ドメイン固有の品質ゲート

以下を下回ったら止める・別 Issue に切り出す基準:

- **親子同期の非破壊性**: `apply-base` 実行後、子固有資産（`.claude/skills/` 等のユニーク名で配置したファイル）が 1 件も消失・上書きされていないこと（自己検査スクリプトで機械確認する）
- **プレースホルダ置換の健全性**: `bootstrap.sh` 等が `BTC Realtime Chart` / `kai-kou/btc-realtime-chart` を正しく解決し、再実行時に無差別置換（既知の 3 欠陥の再発）を起こさないこと（`tools/check_base_sync_integrity.py` で機械確認する）
- **ドリフトの可視化**: 親ベースと下流間の共通ルールの差分を「気づかれないまま放置」しないこと（機械検知が M-1 の必須要件）
- **C-2 の「選定」原則**: 生成するドキュメントが既定で 1 本のみであること（ユーザーが増やすことを明示的に要求しない限り、雛形一式を先回りで置かない）

## SP 工程別標準値（session-sprint-rules.md §3.2 の実体・#45）

> `session-sprint-rules.md` §3.1 のベーススケール + §3.1.5 Dynamic 補正を、本プロジェクトの工程に当てはめた **暫定値**。
> **実測（`content/analytics/sprint/` の tokens/sp・分/sp 中央値）が 4 週分貯まったら @owner が較正する** （§6）。
> 暫定値は「人間工数の直輸入」ではなく、本ベース自身の開発（全て AI 実行）で観測した規模感から置いた初期値。
> プロジェクトごとに自分の工程に置き換える。

| 工程（本ベースの典型タスク） | ベース SP | 備考 |
|------------------------------|-----------|------|
| 状態ファイル / データ更新・1 行修正 | `sp:1` | 機械的変更 |
| 単一ルール / ドキュメントの軽微改修・typo 級 Try | `sp:2` | 単一ファイル |
| 中規模ルール追加・単一ツール改修・スキル frontmatter 調整 | `sp:3` | 標準タスク |
| 複数ファイル横断改修・新ツール追加・脱ドメイン化・要 Agent Teams 議論 | `sp:5` | SSOT 同期を伴う |
| 新スキル設計・フック新設・アーキテクチャ変更 | `sp:8` | 分割を検討（§3.1） |

**Dynamic 補正（横断適用・+1〜2 SP）**: 上記ベースに対し、要リサーチ・仕様未確定・新規領域・clarification 見込みが高い場合に加算する。SP は離散値（1/2/3/5/8）なので、加算結果は最も近い上位スケールに丸める。

- 例: 「最新情報リサーチを伴う新ルール設計」= 中規模ルール（`sp:3`）+ Dynamic（+2・リサーチと議論で不確実性大）= `sp:5`。
- 例: 「公式仕様の確認を伴う単一ツール改修」= 単一ツール改修（`sp:3`）+ Dynamic（+1）→ 近い上位の `sp:5` に丸める。
- **上限**: ベース + Dynamic が `sp:8` を超える場合は `sp:8` でキャップせず、`session-sprint-rules.md` §3.1/§3.1.5 に従いタスクを分割する（8 超のラベルは付けない）。

> **較正の約束（gaming 防止・§7）**: 本表は実測（tokens/sp）に基づき更新するが、velocity（done_sp）や tokens/sp 自体を目標値・ノルマにはしない。あくまで「見積もり精度を上げる」ためだけに使う観測値。
